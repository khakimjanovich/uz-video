Monday, ten in the morning. Aziz sits in a café, on the café Wi-Fi, and logs in to the mobile bank. He types his password, then the code from the SMS. It is the right code, and still the app says: We cannot complete this now. Why would a platform refuse a correct code? The counters of lesson nine guard the code itself: its life, its tries, its requests. They cannot see where the code arrived, but TAF can. And TAF works only in the master app, the mobile bank. First, what TAF is. It is a state service of the mobile operators. Its agent already runs in the bank's network, and heeyID talks to it only through its TAF adapter. In the master app, TAF sends every code for a registration and a login. Its part inside the app checks that the SMS arrived on this phone, with this SIM card. Then TAF gives a verdict. The most important word in this lesson is recommendation. The verdict is advice. The platform makes the decision, with the policy of the bank. The app has a job too. It starts the TAF part after an install. It sends the identifier of that part with each code request. It gives each typed code to the TAF part first. And it tells the TAF part at each logout. If the app skips a step, the verdict simply comes back negative. After a correct code, the platform asks TAF for two verdicts. The basic verdict is seven plain answers: the account is active, the code is usable, the SMS was sent, the status is valid, the code was verified, the device and the SIM card match, and the phone is not a clone. The risk verdict is a colour: Green, Yellow or Red, with a main reason. The risk verdict can take a moment, so the platform asks again at a set interval, until the configured waiting time ends. If it is still not ready, the basic verdict decides. All seven answers true means Green. One false answer means Red. The platform records the result, where it came from, and whether the device and the SIM card matched. Lesson sixteen needs that SIM match. Back to the café. The risk verdict did not arrive in time. On the café Wi-Fi, the device and the SIM card did not match, so the basic verdict said Red. Red means refuse. The login attempt ends. But a refusal blocks nothing, and it changes no counter. The app shows one piece of advice: use the mobile network of your operator, not Wi-Fi. Aziz switches off the Wi-Fi and tries again. This time the risk verdict arrives in time, and it is Green. The login continues, with the SIM match on record. Yellow is the careful colour. It also means refuse, with the reason text of TAF, in the language of the journey. The texts come from the configuration of the bank, and again, nothing is blocked. Aziz is at level one, so his login asks for nothing more. At level two, a login after Green also asks for the face biometric of the phone. This is not MyID, and it gives no level. If the face check of the phone fails, the login stops, and the customer can try again. If the phone has no face biometric at all, the login continues, and nothing goes to TAF. When the check succeeds, the platform sends a face confirmation to TAF, with the personal identification number and the phone number. The platform sends it, never the app, so the personal identification number never reaches the phone. If TAF does not answer, the login still continues, and the confirmation waits for the next login. The same confirmation also comes before the phone ownership check of lesson fifteen. TAF can also be down. The platform checks its health at a set interval, and each call has a timeout. When TAF does not answer, the SMS vendor sends the code. The attempt is marked not scored. There is no verdict, no face confirmation, no ownership check, and no SIM match. The platform writes an audit event, tells the bank's antifraud system, and alerts operations. When TAF is back, the next code goes through TAF again. And one case is not an outage. On the state services portal, a person can choose one trusted bank. If a person chose a different bank, TAF refuses to send the code. The app tells the person to change the setting on the portal, or to contact the bank. Last, what TAF receives. The phone number, a request identifier, the code, the type of message, the device model and the language. The personal identification number goes only with the face confirmation. The phone ownership check sends only the identifier of the TAF part. Never a name, a document, an address or a photo. Now suppose TAF refuses a code because the person chose another bank on the portal. Does the SMS vendor send the code instead? No: the refusal is not an outage, so the platform stops and sends no code through any channel. In the master app, TAF sends the code and gives a verdict. The platform decides: Green continues, Yellow and Red refuse. When TAF is down, the code still comes, but not scored. When the person chose another bank, no code comes. Every one of these logins began with a password, before any code. Lesson eleven shows how the platform keeps that password.
