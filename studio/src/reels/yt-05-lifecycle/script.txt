Can a merchant jump straight from signing up to taking payments? Without rules, one wrong update could switch on a shop nobody ever checked. So a partner moves through fixed states: pending, verified, waiting for a contract, approved, and active. The allowed moves live in one table inside the status enum, and every other move is refused. An illegal jump, like pending straight to active, answers four oh nine with a stable error code. An admin verifies the documents, but only after the merchant has verified its email. Signing the contract approves the partner, and the database keeps every contract number unique. Every change writes a row to the status history: from where, to where, who, and why. Each row is saved in the same transaction as the change, and is never updated. An active merchant can be suspended and restored, or terminated for good. Activating and restoring both end in active, so each one is allowed only from its own starting state. Until logins arrive, the admin is named in a request header. Unit tests check the whole transition table, and integration tests run the lifecycle on a real Postgres. Under load, about three thousand merchants went through the whole lifecycle in thirty seconds, and every check passed. Next, we make sure no single admin can switch a merchant on alone.
