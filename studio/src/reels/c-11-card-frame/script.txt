How do thieves steal card numbers without breaking into any database? In lesson five, the card frame was the bank's card reader on ecom's payment page. In lesson ten, the card zone checked a card's first digits before asking any network. This lesson protects the frame itself, inside the buyer's browser. They add one line of script to a payment page. It might arrive through a hacked analytics tool, or a changed file on a shared server. That one line copies every card number as the buyer types it, and sends it away. The page still works. The buyer still pays. Nobody notices for weeks. This is called web skimming. The card zone's answer is the card frame. The frame is the card zone's own small page, on its own address. It sits inside the bank's payment page like a window. Think of it as the bank's card reader on the shop's counter. A real card reader has tamper seals. The frame has seals too. Seal one: only the page its session names may hold the frame. Each time a buyer pays, the card zone opens a session for one page. A look-alike site that tries to hold the frame is refused by the browser. Seal two: a Content Security Policy. That is a rule the frame gives the browser. It says: run nothing but my own two files, and talk only to my own address. Any other script is refused before it runs. Seal three: Subresource Integrity. The frame names each of its two files by a fingerprint. If even one character of a file changes, the fingerprint no longer matches, and the browser will not run it. When the buyer finishes, the frame hands back only two things: a token and the masked number. It hands them only to the one page its session names. The card number itself never leaves the frame for the page. When the browser blocks something, it reports it to the card zone. So a tampering attempt leaves a trace. And the shop's page around the frame is watched too, because a skimmer there could still trick the buyer. Now watch the product. The buyer opens the payment page. The frame appears inside it, with two fields: card number and expiry date. As the buyer types, the number falls into groups of four. The expiry date gets its slash by itself. The buyer presses "Send code", types the code from their phone, and presses "Confirm". The frame says "Card accepted" and clears the number field. The page shows only the masked line. Now try to break it. Open the frame's address on its own, outside the payment page. It shows one sentence: this page opens only inside the payment page. No form appears. Put the frame inside a look-alike site. The browser shows an empty, refused box instead. Now act as a skimmer. Inside the frame, try to load a script from another address. The browser's console shows a red line: the script is refused under the frame's policy. Nothing loads. On the bank's side, that refusal arrives as a report. The team sees it in the card zone's logs, with the rule that was broken and the page it came from. No card data is in it. What does this protect? It protects the one moment a card number exists in plain view: in the buyer's browser, as it is typed. A database can be locked and sealed, and a skimmer can still copy numbers at the keyboard. The seals protect the buyer from a stranger's script. They protect the bank from a stolen form. And they protect the shop, whose page never touches the number. Back to the card reader. It runs only the bank's software. It works only on one counter. And a broken seal shows. Next: the two doors into the locked room.
