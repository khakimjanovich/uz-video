When a payment is slow or stuck, how would anyone know? One payment crosses the app, an adapter and a scheme, and the logs on each machine can't follow it. So every service runs with the OpenTelemetry Java agent, attached by the infrastructure, with no change to the code. It traces every HTTP call in and out, every database query and every Redis command, and hands the trace on to the next service. One trace follows a payment from the payment page, through the app's modules, into the Uzcard adapter and out to the scheme. The logs carry the same trace id, so a warning links straight to the trace it belongs to. The agent also exports JVM, HTTP and database pool metrics, and the app adds only what the agent can't know: how payments end. Every debit is counted by card scheme and outcome: approved, declined, unknown, or failed before any money moved. And the scheme's answer time is measured, with fixed buckets up to its forty second limit. Everything goes over OTLP to one stack: Prometheus for metrics, Tempo for traces, Loki for logs, and Grafana on top. The payments dashboard puts it together: debits by outcome, unknown debits in red, answer times, errors per service, and pool waits. When the scheme went silent, the dashboard showed one unknown debit and a failed call in the adapter, a five oh two, and the warning linked to its trace. Locally every trace is kept; production samples them, and the load stack runs without the agent, so k6 still measures the code alone.
