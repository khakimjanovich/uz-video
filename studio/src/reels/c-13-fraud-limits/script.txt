How do you stop someone testing stolen cards on a payment page? Picture a thief with a bag of keys. They try key after key in a shop's lock, to find the ones that fit. Locking that door after three wrong keys does not help. They just walk to the next door. Here, the keys are stolen card numbers. The doors are payment sessions. A thief buys ten thousand stolen numbers. Most of them are dead. To find the live ones, they try them on a small shop's payment page. That is called card testing. Every try reaches a card network. Every try may text a code to a real person's phone. So card testing costs the bank money, floods strangers with codes, and hands the thief a list of working cards. Each session already allows only a few tries. When they run out, the session ends. But the thief just opens a new session. So counting per session is not enough. The card zone counts the keys, not the doors. It writes every attempt down before any network is asked. Attempts made at the same moment count each other, so speed does not help the thief. Each attempt is kept by four things. The card, by its fingerprint, never its number. The card's first digits. The buyer's address on the internet. And the shop. The bank chooses a limit for each of the four, and a time window. So many failed tries per card, per first digits, per address and per shop, within that window. These are the bank's chosen limits and the bank's chosen window. A limit on tries within a time window is called a velocity limit. Past any one of the four limits, a new try is refused before any network is asked. No code is sent. No attempt is spent. And no new session opens for that shop until the window passes. Only failures that say something about the card count against it. A wrong code counts. A card the buyer's bank refuses counts. A mistyped expiry date does not hold back a whole group of cards. And the card zone's own failures, such as a network being down, never count against anyone. When refusals pile up, an alert goes out to the team. Now watch the product. A buyer types the wrong code. The form says the code is wrong, and how many tries are left. The buyer runs out of tries. The form clears. The payment page shows a yellow note: that attempt ended, too many tries or the time ran out, enter the card again. A fresh, empty form appears. That is a normal buyer having a bad day. Now the thief, with a script, fires card after card. For a while, each card is just refused. Then a counter reaches its limit. From that moment, the form answers every new card the same way: "Too many unsuccessful attempts. Try again later." No code is sent. No network is asked. No stranger's phone buzzes. On the bank's side, an alert email arrives. It says card entry was refused by a velocity rule. It names the caller, and the counter that tripped: the card, the first digits, the address, or the shop. It tells the team where to look next: the logs, and the buyer addresses behind the refusals. What does this protect? It protects cardholders, whose phones would otherwise fill with codes. It protects the shop, whose page would otherwise become a thief's testing bench. And it protects the bank, which would otherwise pay for every try and hand thieves a list of live cards.
