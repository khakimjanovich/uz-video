Where should a new feature start? Picture a developer who starts with the table, because the table is what they can see. The API mirrors the table, and the status column takes any string. Six months later, suspended merchants are taking payments, because nobody wrote down which moves are allowed. A board game is designed the other way round. The rules come first: which moves are legal. Then the printed rulebook, which is hard to change once players have it. Then the board, and only then, play. Every feature in this system is built in the same order. First the rules: a partner, and its state machine. A state machine is the list of allowed moves, and any other move is refused. A new partner is verified, then waits for a contract, then for approval, and only then goes live. A live partner can be suspended and brought back, and a closed one stays closed. Second, the rulebook: the contract, which says what callers may ask, and what they get back. The controller implements an interface generated from it, so the code cannot drift from the contract. Third, the board: the module's own schema in the database, reached by its own user, which sees nothing else. Each change to the schema is a changeset: it runs once, and it is never edited. A new change is always a new changeset on top. And other modules keep only a partner's id, never a link into its table, so the module can move out one day. Last, play: the smallest code that makes it all work. Even an error follows the rulebook. Ask for a partner that does not exist, and the answer is a problem detail. A problem detail is a standard error answer, with a stable code, and a message in the caller's language. Now read the rules in the code. The partner's states are listed once, and one method says where each may move next. A terminated or rejected partner can move nowhere. And the missing partner is one entry in a short file: four oh four, a stable code, and the message in English, Russian and Uzbek. Rules, rulebook, board, then play: the order of every lesson from here. Next module: the merchants, starting with how they sign up.
