It is two in the morning, and Aziz's phone buzzes. A code from the bank. Then another one. He did not ask for any of them. Somewhere, a script types his number into the marketplace web page, again and again. Who stops it, and who stops the next step, when the script starts to guess the code? In lesson ten, the platform made a random code for a registration and kept it only as a digest. This lesson shows the rules around that code: how long it lives, how many tries it gets, and how many codes one number, one address or one device can ask for. Start with the code itself. It is random, with enough digits that a guess is very unlikely. The platform keeps it in a small table of codes in Postgres. It does not keep the code. It keeps a keyed digest of it, made with the code pepper, a secret that lives in Vault, as lesson eight showed. So a copy of the database gives nobody a code. Each new code also makes the older codes of the same journey void. So at any moment, one code is alive. The code is never in clear at rest, not even after it goes to TAF, and it never goes to a log. When Aziz types a code, the platform compares the digests in constant time. A wrong code and a nearly right code take the same time to answer, so the timing tells an attacker nothing. Now the limits on one code. Each is a policy that the bank sets. The code has a short lifetime. It accepts only a few wrong entries. Then the answer is: wrong code, and the number of tries that remain. After the last wrong entry, the code is void, and the person must ask for a new one. A new code needs a minimum interval since the last one: ask too soon, and the answer is wait, then ask again. And each journey gets only a few resends. One more limit comes from outside. TAF has its own lock: after a few wrong codes, it blocks the number for a while. So the platform's limit on wrong entries may never be looser than the TAF limit. If it were, TAF would lock Aziz out before the platform even counts. So guessing one code does not work. But the script at two in the morning does not guess. It simply asks for new codes. That is where the rate limits come in. The platform counts three things, in the time zone of the installation. The code requests for each phone number in one day. The code requests for each network address in one hour. And the registrations for each device in one day. The bank sets each limit. The script hits the limit for Aziz's number. Its next request gets one answer: too many requests, try again at the given time. The platform writes an audit event, and sends an event to the bank's antifraud system. Aziz's phone goes quiet. Where do these counters live? In Valkey. A counter there can carry its own expiry, so a cool-down simply runs out by itself, and a read takes less than a millisecond, even at peak load. And nothing in Valkey is the only copy. Each value there either comes again from Postgres, or expires. I think the most important rule in this lesson is a short one. A limit in the app is only for convenience. The app can grey out a button, but only the server counts. The script at two in the morning never opened the app. It called the API directly, and the API still said no. The same idea guards a much more expensive call, which comes later in the course: MyID. The platform counts failed MyID attempts for three subjects: the phone number, the device, and the personal identification number when it is known. When one subject reaches a limit, the attempt is refused. There is a daily cap, a cool-down after the first counted failure, and a longer cool-down after the second. The refusal tells the person the earliest time of the next try. Only a failure that the person caused counts. A face that does not match counts. MyID being down does not. An operator can reset the counters, with a reason. And test customers are never counted. To recap. One code, kept as a keyed digest, with a short life and only a few tries. Rate limits for the number, the address and the device. Counters and cool-downs in Valkey, and every decision on the server. But think about the code that Aziz typed correctly on Monday. It was the right code. Was it typed on the phone that really holds his SIM card? Next: the TAF verdict.
