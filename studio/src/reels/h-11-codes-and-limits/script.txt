That night, at two in the morning, Aziz's phone buzzes. A code from the bank. Then another one. He did not ask for any of them. Somewhere, a script calls the registration of the mobile bank with his number, again and again. Who stops it, and who stops the next step, when the script starts to guess the code? That afternoon, Aziz registered with a code like these, and the platform kept only a fingerprint of it, as lesson eight showed. Tonight a stranger asks for the same kind of code. This lesson shows the rules around it: how long it lives, how many tries it gets, and how many codes one number, one address or one device can ask for. Start with the code itself. It is random, with enough digits that a guess is very unlikely. The platform keeps it in a small table of codes in Postgres. It does not keep the code. It keeps a keyed digest, made with the code pepper, a secret that lives in Vault, as lesson six showed. So a copy of the database gives nobody a code. Each new code also makes the older codes of the same journey void. So at any moment, one code is alive. The code is never in clear at rest, not even after it goes to TAF, and it never goes to a log. When Aziz types a code, the platform compares the digests in constant time. A wrong code and a nearly right code take the same time to answer, so the timing tells an attacker nothing. Now the limits on one code. Each is a policy that the bank sets. The code has a short lifetime. It accepts only a few wrong entries. Then the answer is: wrong code, and the number of tries that remain. After the last wrong entry, the code is void, and the person must ask for a new one. A new code needs a minimum interval since the last one: ask too soon, and the answer is wait, then ask again. And each journey gets only a few resends. One more limit comes from outside. TAF has its own lock: after three wrong codes, it blocks the number for ten minutes. So the platform's limit on wrong entries is never more than three. With a higher limit, TAF would lock Aziz out before the platform even counts. So guessing one code does not work. But the script at two in the morning does not guess. It simply asks for new codes. That is where the rate limits come in. The platform counts three things, in the time zone of the installation. The code requests for each phone number in one day. The code requests for each network address in one hour. And the registrations for each device in one day. The bank sets each limit. A fourth counter watches the whole installation: all the code messages in one hour. At its alert level, operations get an alert. The script hits the limit for Aziz's number. Its next request gets one answer: too many requests, try later. The platform writes an audit event, and sends an event to the bank's antifraud system. Aziz's phone goes quiet. These counters live in Valkey. A counter there can carry its own expiry, so a cool-down, the wait before the next try, simply runs out by itself. And a read takes less than a millisecond, even at peak load. The wrong entries of each code are a counter there too, and that counter ends with the code. And nothing in Valkey is the only copy. Each value there either comes again from Postgres, or expires. The most important rule in this lesson is a short one. A limit in the app is only for convenience. The app can grey out a button, but only the server counts. The script at two in the morning never opened the app. It called the API directly, and the API still said no. The same idea guards a much more expensive call: MyID. Lesson thirteen shows its own counters and cool-downs. Now suppose the script slows down: one request each hour, each time from a new network address. Which counter still stops it? The counter for his phone number, because it counts every code request for that number in one day, from any address. One code, kept as a keyed digest, with a short life and at most three wrong entries. Rate limits for the number, the address and the device, and an alert for the whole installation. Counters and cool-downs in Valkey, and every decision on the server. The code that Aziz typed on Sunday was right, but a right code is not the whole story. TAF also checks where it arrived, and lesson ten shows that verdict, on a Monday morning in a café.
