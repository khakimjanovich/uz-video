What stops one admin from switching on a fraudulent shop? Right now one person can, so one mistake or one bribe is enough. So activation becomes a request: one admin, the maker, asks, and nothing changes yet. The single-admin activate call is gone, and three new calls take its place. A different admin, the checker, approves it, and only then does the merchant become active. A request is decided once: it must still be pending, not expired, and the checker can't be the maker. Self-approval answers four oh nine, with its own error code. The checker's name goes into the status history, with the maker in the reason. Requests expire after a configured time, twenty-four hours here. A scheduled sweep marks overdue requests as expired, and ShedLock makes sure only one instance runs it. Only one pending request per merchant can exist, and a partial unique index in the database enforces it. Integration tests on a real Postgres prove the approval, the index, and the sweep. Under load, almost three thousand merchants were activated by two admins in thirty seconds, and every self-approval was refused. Next, real logins, so an admin's name comes from a token instead of a header.
