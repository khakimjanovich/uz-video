How does the bank know a new merchant really owns the email they typed? Anyone can type any address, so a sign-up alone proves nothing. The contract adds three calls: register, verify the email, and resend the code. Registering saves the merchant as pending, and refuses an email that is already taken. A one-time code then goes to that email, from the OTP library that any module can use. Redis keeps only keyed hashes of the code and the email, and one script checks every limit and stores the code in a single step. The email goes out through the notification service, and locally it lands in Mailpit. The merchant sends the code back, and only then is the email marked as verified. Wrong codes count across the whole send window, so a lockout lasts until the window ends, even for a new code. Sends are limited per window, and a new code waits a configured pause after the last one, so nobody can flood an inbox. Every refusal that lifts by itself carries a Retry-After header that says when. Without Redis, no code is sent or accepted: the library fails closed with a five oh three. Every failure has its own stable code, and its message in English, Russian and Uzbek: email taken, code invalid, code expired, too many attempts, or too early. The limits are the library's own defaults, and the app supplies only the secret, from Vault. Next, the merchant moves through a lifecycle, from pending to active.
