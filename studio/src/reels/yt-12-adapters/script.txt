How does our system talk to Uzcard and Humo, when they speak different languages? Uzcard's SV-Gate speaks JSON-RPC, and Humo speaks SOAP for payments and REST for cards, each with its own fields and codes. If the payment code knew both, every new scheme would mean touching payment code, and no other project could reuse the work. So each scheme gets its own adapter: a separate Spring Boot service with its own OpenAPI contract, that any service or project may call. Every adapter answers plain REST with one envelope: a request id, the scheme's own status, and its data in the scheme's own field names. Inside, every scheme method is one command, picked by its type from a factory, calling the scheme through typed models and one HTTP interface client per area. What each scheme code means lives in a status table: success, error, pending, not found, unavailable, or manual review. The card module turns a scheme's decline code into its own: insufficient funds, expired card, or limit exceeded. Uzcard debits in one step, by the card's token, with our payment id as the external reference. If that reference was sent before, SV-Gate refuses it as a duplicate, the adapter answers pending, and a lookup by the reference tells the outcome. Humo holds the money first, and the card module captures it right away; a hold whose capture got no answer is captured when its status is asked. Humo settles a terminal's payments only after reconciliation, so the card module reconciles every Humo e POS terminal before each clearing session. The app wires each adapter's generated clients as one HTTP service group, and the card module sees only one port, a card processor, per scheme. Every answer becomes one of three outcomes: approved, declined with our own code, or unknown. A timeout, a redirect, or an answer it cannot read is the adapter's client error, a five oh two, and the card module reads it as unknown, never a decline, because the money may already have moved.
