How does our system talk to Uzcard and Humo, when they speak different languages? Uzcard speaks JSON-RPC, and Humo speaks SOAP, with different fields and different errors. If the payment code knew both, every new scheme would mean touching payment code, and no other project could reuse the work. So each scheme gets its own adapter: a separate Spring Boot service with its own OpenAPI contract, that any service or project may call. Every adapter answers plain REST: an envelope with a request id, the scheme's status and the data, or a problem detail that carries the scheme's own code. Inside, every scheme method is one command, picked by its type from a factory, the same way in both adapters. A status file in each adapter turns every scheme code into a status, and the card module turns the scheme's decline codes into our own. Uzcard debits in one step, by the card's token, with our payment id as the external reference; if that reference was sent before, Uzcard answers pending instead of paying twice, and a lookup by that reference settles it. Humo holds the money first, and the card module captures the hold right away; a capture that gets no answer is taken on the next lookup. The card module needs only the published client library and one port, a card processor, with one processor per scheme. Every answer becomes one of three outcomes: approved, declined with our own code, or unknown. A timeout answers five oh two, and the card module reads it as unknown, never a decline, because the money may already have moved. Next, knowing a card's scheme, and storing its number safely.
