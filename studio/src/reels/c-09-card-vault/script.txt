How do you keep a card number so that even a stolen database is useless? In lesson five, the card went straight into the card zone, and only a token came back. In lesson six, Vault held every key, and no key was ever typed into a file. This lesson uses Vault to seal each card number, so even a stolen database is useless. Picture the worst day. A copy of the database leaks. If the card table holds numbers, every card is gone. If it holds numbers locked with a key that sits next to them, every card is still gone. So the key must never sit next to the data. Remember the locked room from earlier lessons. Inside it, every coat goes into a sealed bag. Only one machine can seal a bag or open it. That machine never lends out its key. In the card zone, that machine is Vault. The card vault, the service that keeps cards, hands Vault the card number. Vault hands back a sealed value. The card vault keeps only the sealed value. The key never leaves Vault. Each seal is tied to its own card. A sealed value copied into another card's place will not open. So nobody can shuffle bags to trick the room. Now a puzzle. Sometimes the card zone must find a card again by its number. It must do that without opening every bag. So Vault also stamps each bag with a fingerprint. The same number always gives the same fingerprint. The fingerprint cannot be turned back into the number. This stamp is called a blind index. The card zone looks up the fingerprint, never the number. The database guards the door too. It refuses any card value that is not sealed. Even a mistake in the code cannot write a plain number into it. What if Vault is down? Then the card vault stops. It never guesses, and it never falls back to keeping a plain number. Stopping safely instead of carrying on unsafely is called fail closed. A number is opened for one reason only: to hand it to the card's network for a charge. Every use of card data is written down: what happened, who asked, and when. And a card nobody has used for the bank's chosen time is removed. Only a short note keeps its token and its masked number. Now watch the product. There is no screen inside the locked room, so watch what each side sees. The buyer types a card into the card form and confirms the code. The form says "Card accepted" and empties its number field. The payment page then shows one line: the first six digits, a row of stars, and the last four. Beside them sit the card's network and the bank that issued it. That masked line is all anyone outside the room ever sees. Now Vault stops answering. The buyer types a card, and the form refuses it with a short message. Nothing is saved, sealed or unsealed. On the bank's side, the team gets an alert: a service the card zone depends on is unavailable. The alert names the part that failed. Once Vault is back, the same card goes through. Now the leaked copy again. An attacker opens it. They find sealed values, fingerprints and masked numbers. The keys are not there. A backup is just as useless without the Vault that sealed it, so the bank keeps both, and keeps them apart. What does this protect? It protects every cardholder whose number has ever passed through the room. A stolen database, a stolen backup, or a curious insider all see noise. And the bank is protected too, because a leak of noise is not a leak of cards. Back to the sealed bags. A machine that keeps its key. A stamp that finds a bag without opening it. A database that refuses anything unsealed. So a stolen copy of the database is just noise. Next: what a card's first digits tell you.
