Aziz has been our hero for thirty-seven lessons, but he is not a real person. The test team needs him every day: registered, proved, blocked, refreshed, and proved again. MyID, though, is a state service that proves real people from state records. So how does the team run Aziz's journeys through MyID, without the data of a real person, and without one test record ever reaching production? In lesson seven, simulators stood in for each outside service, and in lesson thirty-seven, the panel kept every change to configuration under maker-checker. This lesson puts those pieces into two zones, and gives Aziz a test identity. First, the zones. The bank runs heeyID as two separate installations. Stage lives in the test zone of the bank, and production lives in the production zone. Each one has its own MyID credentials, its own connections to the bank's services, and its own data. Stage connects only to the MyID test environment, and production connects only to the MyID production environment. Neither installation can reach the environment of the other, and there is no network route between the zones. Only configuration moves from stage to production. Customers, devices, sessions and audit events never move. Second, the test identity. MyID has a test environment, with test identities registered there. The stage configuration lists them. Each one has a personal identification number, or a document series and number, and the result that it must give: success, or a named failure reason. For example, one identity succeeds, another fails because the face does not match, and another fails because the document has expired. So the acceptance tests run the same journeys with the same results, every time. Third, the test flag. Each customer that the platform creates in stage uses a MyID test identity and carries a test flag. Limits and reports never count test customers. In production, every customer is a real person that the MyID production service proved. That includes the people the bank uses for its own checks: in production they are normal customers, under every rule of this course. I think that rule is the honest one: production has no back door called test. Fourth, the guards that keep the zones apart. A production build does not start when its MyID host is a test host, or when test customers are allowed. In the production zone, the database itself refuses a customer row with the test flag. And the move from stage to production is only a difference in Helm values, which a second person approves, so no database content moves. Fifth, the simulators. Every acceptance test can also run with no MyID, no SMS service, no push service, no customer lookup and no antifraud system. The simulators give each reason code and each answer that the real services can give. So a developer can run the whole suite on a laptop, with no internet. Each night, a second run goes against the MyID test environment and adds to the simulated run. Back to Aziz. In stage, he is a test identity with a known result. On a developer's laptop, he is a simulator that never gets tired. And in production, he does not exist at all, which is exactly right. To recap: two zones, two installations, two MyID environments, and no route between them. Test identities with expected results, a test flag that limits and reports ignore, and guards that stop a test value in production. But one question is still open for the whole course. Who builds these two installations in a new bank, from nothing, and how do we know that the build is done? Next, the last lesson: installing heeyID.
