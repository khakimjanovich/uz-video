Saturday, one in the morning, the stolen phone lights up in the thief's pocket. It is a push from the bank. The thief leans in to read it, and finds nothing worth reading. Why does a message from the bank carry so little, on purpose? In lesson twelve, TAF sent the codes in the master app, and in lesson twenty-six, the bank's SMS service sent them in the side apps. This lesson collects every message the platform sends: which road it takes, whom it may reach, and what it may say. First, the roads. The platform has no messaging contract of its own. Every SMS goes through the SMS service of the bank, and every push goes through the push service, in the Firebase project of the bank. Codes follow the app. In the master app, TAF sends the code, and the bank's SMS service sends it only while TAF is down. In a side app, on a phone or on the web, the bank's SMS service always sends it. Only the code message carries a code, and a push never does. Second, the addresses. An SMS goes only to the number of the registration, or to the verified number of the customer. A push goes only to the devices of the customer. Now, how does a message leave without getting lost? Say Aziz changes his password. In the same database transaction, the platform writes the new password digest, and a row in the outbox: send password changed. A relay publishes that row to Kafka, and a worker hands it to the SMS service or the push service. If the platform crashes in the middle, the row is still there, and the relay sends it later. And if the change itself fails, there is no row, so there is no message about a change that never happened. The services send back delivery reports, and the platform records them. A failed dispatch goes again, as often as the configured retry policy says, and then the platform records it as failed. Third, what must be sent. Some messages are security notifications, and the customer cannot switch them off. A new session sends a push to all his other sessions, and an SMS to his verified number, with the app, the device model, the network address and the time. A login from a new device, a password change, a locked password, a block, an unblock: each one has its own template, and each one goes out. Now the rule from lesson thirty-one. When Aziz taps this was not me, his number goes on hold. From then on, every message goes by push only, and no SMS goes to that number while it is on hold. The reason is simple: the person who holds that SIM card may be the person Aziz is running from. Fourth, what a message may say, and this is where the thief comes back. No message contains document data or the personal identification number. No message has a name other than the first name, and no message has a link that starts an action. A message about a login may show the device model, the network address and the time. And a push never contains a code, a text or personal data. It carries only the type of the message and a reference. The app gets the words afterwards: it asks the platform for the text with the reference. Only a device of the customer can get that text, in the customer's language, from the template version that was published when the message left. So the thief on Saturday night sees, at most, which kind of message the bank sent. I think this is the most honest design for a phone that can be lost: the push is a doorbell, not a letter. The push service is outside the bank's perimeter, so it learns nothing about Aziz either. And when the push service is down, notifications go by SMS only. Last, the words themselves. Each template exists in the four languages. Compliance changes a template with maker-checker, and the platform keeps every version. The audit event of each message names the version that was sent. To recap: two roads, the bank's SMS service and the push service, and codes by TAF in the master app and by the bank's SMS in side apps. An outbox so nothing is lost, security notifications that nobody can switch off, no SMS to a number on hold, and pushes that carry only a type and a reference. But each of these messages also became an audit event. Months from now, someone will ask what really happened on Friday night. How does the bank prove it, and prove that nobody changed the proof?
