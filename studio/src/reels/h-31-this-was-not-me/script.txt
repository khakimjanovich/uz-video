Wednesday, eleven at night. Aziz is watching a football match when his phone buzzes. The mobile bank shows a login request from a phone he has never owned, at an address he does not know, one minute ago. Under it: Approve, and This was not me. Aziz taps This was not me. One tap. What must the platform do now, and what must it not do? In lesson thirty, the stranger with Aziz's SIM card tried a reset, and MyID stopped him. This lesson follows his other try, a normal login with a guessed password, and the button that answers it. First, how the request reached Aziz. The stranger typed Aziz's number and the correct password on a new phone. Only after a correct password does a new-device request start. TAF sends the code to the number, so it lands on the stranger's SIM card. At the same time, the platform finds Aziz's session in the mobile bank. It has rank two, so it gets the approval request. The push carries no code, only the request identifier. The new phone needs both: the code and the approval. Now Aziz refuses. Step one is the obvious one. The login on the new phone is refused, the attempt ends, and an event goes to the bank's antifraud system. But think about what this tap means. The request started only after a correct password. So someone knows Aziz's password. And that someone may also hold his SIM card, because the code went to that number. Every new code and every SMS alert to that number may land in a stranger's hand. So step two: the number goes on hold. While it is on hold, the platform starts no login that needs a one-time code to this number, on any phone or browser. It sends no SMS to the number at all. Notifications go by push only. So the marketplace website cannot help the stranger either: a web login that needs a code is refused. And Aziz's own sessions keep working, because their access does not need the number. Step three happens on the phone that refused. The mobile bank asks Aziz to change his password, at once. He types the old one, then a new one, two times. As after each password change, the other sessions of the same or a lower rank end. Aziz's session has rank two, so every other session ends, including any that the stranger opened. Step four is one question. Does your SIM card still work? If Aziz says yes, the stranger had only the password. The new password fixes that, and the hold ends. If Aziz says no, the stranger has his SIM card. Then the number must leave the account. Aziz was at level two, so first he passes a MyID re-check, on this phone. Then the platform removes the number, the same way as a number reassignment, and Aziz adds a new number. His account is not blocked at any point. At each step, the platform writes an audit event and sends an event to the antifraud system. And it sends the notification, number on hold. Why a hold, and not a removal at once? I think the answer is the wrong tap. People tap the wrong button, at eleven at night, during a football match. If This was not me removed the number at once, one wrong tap would take away Aziz's only login. The hold is safe and easy to undo. The SIM question decides the rest. The design pays a price for this. SMS notifications stop while the number is on hold. And a customer who has no session on any device cannot end the hold alone. A bank operator ends it, with a reason. One more detail. Only a rank-two session can refuse. A session of rank one, like a marketplace browser, gets a notification about the new login, but no buttons. Otherwise, a stranger with an old web session could approve his own login. To recap: This was not me refuses the login. Then the number goes on hold: no codes, no SMS, push only. The password changes at once, and the other sessions end. Then the SIM question: yes ends the hold, no removes the number after MyID. Aziz said no. His old number is now free, and one day the mobile operator gives it to someone else. When that person registers with it, what does the platform see? Next: when numbers change.
