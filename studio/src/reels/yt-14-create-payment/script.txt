How does the bank know a payment request really came from the shop, and only once? First, a setup chain: the merchant signs up by email code, two admins approve it, its sales point goes live, it gets an e POS terminal, a commission rule, an API client, and a signing key in Vault. The shop's server asks for a payment: a website, an order number, an amount in tiyin, and a return address. Its access token comes from its API client, which carries the merchant role. But a stolen token alone must not be enough to create payments, so every request is also signed. It follows R F C ninety-four twenty-one, HTTP Message Signatures: the server signs the method, the full address, its token, the body's digest, a creation time and a nonce, with HMAC SHA two fifty six. Each API client has its own signing key, which the bank puts straight into Vault; our app never generates it, and only reads it. A key read from Vault is kept only for the configured time, and an unreachable Vault refuses the request instead of falling back to an old key. A signature created outside the configured window is refused, and a nonce works only once, remembered in Redis. The signature is checked before the nonce is spent, so a forged request can't burn the merchant's nonces. A network retry must never create a second payment, so each request carries an idempotency key. The same key with the same body returns the stored response, and the same key with a different body is refused. Two retries at the same moment meet at the database's unique keys, and the loser replays the winner's answer. Only the merchant's own live website, with one of its return addresses, can take a payment, and anything else is refused before saving. The response carries a one-time link to the bank's payment page, and the database keeps only its hash; the payment's other columns come in episodes fifteen, sixteen, twenty and twenty-one. Next, the buyer opens that page and enters their card.
