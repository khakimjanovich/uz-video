How does the bank know a payment request really came from the shop, and only once? The shop's server asks for a payment: a website, an order number, an amount in tiyin, and a return address. Its access token comes from its API client, which now carries the merchant role. But a stolen token alone must not be enough to create payments, so every request is also signed. The server signs the method, the path, a timestamp, a nonce and the body's hash with HMAC SHA two fifty six. Each API client gets its own signing key: Vault joins docker compose and keeps it, and the merchant sees it once. A timestamp outside the configured window is refused, and a nonce works only once, remembered in Redis. The signature is checked before the nonce is spent, so a forged request can't burn the merchant's nonces. A network retry must never create a second payment, so each request carries an idempotency key. The same key with the same body returns the stored response, and the same key with a different body is refused. Two retries at the same moment meet at the database's unique keys, and the loser replays the winner's answer. Only the merchant's own live website, with one of its return addresses, can take a payment, and anything else is refused before saving. The response carries a one-time link to the bank's payment page, and the database keeps only its hash. In k6, five servers created over four thousand payments in thirty seconds, and every check passed. Next, the buyer opens that page and enters their card.
