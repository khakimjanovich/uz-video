How do you keep one app from turning into a tangle? Picture a payments product that starts as one Spring Boot app. Within a year, the payment code reads the merchant table directly, because it was quicker. Then a fee change breaks refunds. Splitting into many small services on day one costs a network hop, a deploy and a database for every feature. There is a middle way: an apartment building. One building, with walled flats, front doors, and plumbing shared by all. ecom is a modular monolith: one Spring Boot app, deployed once, built from five modules. Each module is a flat with walls. A module cannot use another module's code, and if it tries, the build fails. Instead, it knocks on the other module's door. That door is an internal contract: the few operations a module lets its neighbours ask for. Inside one app, the door is answered in the same process. If a module ever moves out, the same door is answered over HTTP, and the caller's code does not change. Each contract is written by hand first, and the code is generated from it, never edited. And every service needs the same plumbing: errors, settings, security, the database. That is the platform library set, written once, and pinned in one line. Now see the wall in the build files. The payment module's build lists only other modules' contracts, never their code. And two architecture rules run with every build. One checks that modules stay inside their own walls. The other checks that controllers call only services. Now break the wall on purpose. Make the payment module import the partner module's repository. Run the build, and it fails at once: the payment module cannot even see that package. Put the file back, and the wall is whole again. One building, walled flats, and one shared set of pipes.
