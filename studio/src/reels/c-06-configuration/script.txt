Thursday night, Timur installs the card zone at the bank. Halfway in, the install stops. One caller's fraud limit has not been typed in yet. The message names the missing value, and the caller it belongs to. In lesson five, ecom and the card zone talked only through a written contract. This lesson shows where every key and setting comes from, and why a missing one stops everything. Timur could wish for a default. Here is what a default costs. Say a payment service shipped with a timeout of thirty seconds, as a sensible guess. In production, nobody sets the real value, so thirty seconds quietly stays. One night the card network takes forty seconds to answer. The service gives up at thirty and tells Malika's site the payment failed. But the card network said yes, and the buyer's money is gone. A guessed default looks safe until production. That is why I would defend one rule in any meeting: no setting has a default value. Every setting comes from one locked store, Vault: a safe for settings and secrets. Three kinds of value go into it. Some belong to the system itself, like which service listens where. Some are secrets, like passwords and keys, and every one of them is generated inside Vault. Nobody types a password into a file, and the product ships none. And some only this bank knows, like the card network's address and the bank's login there. Timur types each of those once, into Vault. Before a service starts, it is handed exactly its own settings, in a private file only it can read. Its own configuration holds only the names of settings, never the values. If even one value is missing, the service refuses to start. It names every missing one at once, not just the first. That is fail fast: stop loudly at the start, instead of failing quietly later. The same rule covers the bank's business decisions. Rates, limits and waiting times are the bank's choices, so each is a setting the bank chooses, never a number hidden in the product. The card zone has its own settings too, and every one is the bank's. The bank chooses which systems may call the card zone, and which roles each caller gets. For each caller, the bank chooses which websites may show the card form, how long a card entry session lives, and how many tries a buyer gets. The bank chooses the fraud limits: how many attempts one card, one group of cards, one address and one shop may make within its chosen time window. The bank chooses how long an unused card is kept before it is deleted, and how often the keys that lock card numbers change. And the bank chooses when the nightly clean up jobs run. So Thursday's missing fraud limit is a real decision, not a typo. Timur types it into Vault and runs the install again. This time, it runs. Settings have no screen, so watch one service start with nothing set at all. It does not start. It prints one message: required settings are missing. Below it comes one line for every missing setting, by name. Nothing half works. Nothing listens with a guessed address, a test password or a made up timeout. Then its settings are handed over, and the service starts. So a wrong guess never reaches production, and a payment never fails on a timeout nobody chose. A test password never guards real money, because no password exists outside Vault. And the bank stays in charge: every limit, window and time in the product is a value the bank chose and can see. Thursday's install stopped for one minute. A guessed limit would have stayed wrong, quietly, until it cost someone money. Next: how every call proves who it comes from.
