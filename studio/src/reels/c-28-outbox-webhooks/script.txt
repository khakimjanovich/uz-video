How do you tell a shop about a payment without ever losing the news, or inventing it? Picture an app that saves a payment as paid, and then tells the shop. If it crashes in between, the shop never hears, and ships nothing. Swap the order, and a crash announces a payment that was never saved: the shop ships goods for free. An office solves this with an outbox tray. You close the file and drop the letter in the tray in one motion, and the postman collects from the tray. Here, the tray is a table called the outbox. When a payment ends, its event is written to the outbox in the same transaction as the final state. Both are saved, or neither is. A relay is the postman: it collects the oldest unsent rows. Two copies of the relay never pick the same row. It publishes each event to Kafka, keyed by its payment, so one payment's events stay in order. It marks a row sent only after Kafka has it. So a crash in between can send an event twice, and that is at-least-once delivery. Every event has its own id, so a repeat is easy to drop. The database stays the truth, and Kafka only carries the news. Now read it in the code. The outbox writer runs while the payment is saved, inside the same transaction. It saves one event row, with its own id, for each finished payment. The relay takes the oldest unpublished rows, and skips any row another relay has locked. And it marks them published only after they are sent. Like the outbox tray: decided and posted in one motion, so the postman may knock twice, but never zero times.
