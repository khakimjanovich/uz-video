Monday, seven in the morning. Aziz logged out of the mobile bank last night, on purpose, because his little nephew plays games on his phone. Now he needs to pay for his bus pass. Same phone, same app, but no session. What must he show to get back in, and in which order? In lesson twenty-two, Aziz reached level two, and his phone became Trusted. This lesson starts a new session on that same phone: the password first, then the one-time code, then the verdict. First, when is a login needed at all? Only after a logout, or when a renewal fails. While a session is valid, the app simply renews it, with no password, as lesson twenty-one showed. Aziz logged out, so this morning he needs a real login. He types his phone number and his password. The app sends them with his device identifier. The gateway does one thing before anything else: it checks the password. It compares the password with the kept digest from lesson thirteen, in constant time. If the number has no customer at all, the gateway still runs a check, against a dummy digest. The answer is the same as for a wrong password, and it takes the same time. So nobody can use the login page to learn who is a customer of the bank. Suppose Aziz types it wrong. The count of wrong entries goes up, and the platform writes an audit event and an antifraud event. At the configured limit, the platform locks password login for the configured time, and sends the notice: password login locked. But a lock is not a block. No session ends, and the lock ends by itself after that time. Aziz types it right this time. Now, why does the password come first, before any code? Here is my view. A code costs money, and it lands on a real phone. If the gateway sent a code to any number that someone typed, a stranger could fill Aziz's phone with codes all night. So the gateway sends a code only after a correct password. A person who knows only the number gets nothing. Now the code. It comes through TAF, the antifraud service of the mobile operators, from lesson twelve. TAF sends it by SMS to Aziz's verified number. The message says it is for a login, and it names the device model. If TAF is down, the bank's own SMS service sends the code instead. That login is then marked not scored. Aziz types the code, and the platform asks TAF for its verdict. Green: the login continues. Red: the login is refused. Yellow, for a customer who was ever at level two: the login waits for consent and a MyID re-check on this phone. Sometimes TAF says that the device and the SIM card do not match. Then the app gives Aziz simple advice: use the mobile network, not the café Wi-Fi. Today the verdict is green. One more step, because Aziz is at level two. The app asks for the face check of the phone itself, the one that unlocks his screen. This is not MyID, and it gives no level. If it fails, the login stops, and Aziz can try again as the phone allows. If it passes, the platform sends a face confirmation to TAF, with his personal identification number. The phone never sees that number. If TAF does not answer, the login still continues, and the platform sends the confirmation again at the next login. Now the gateway is satisfied. It asks Keycloak for a new access grant. The session gets level two, because Aziz is at level two and this phone is Trusted. There is no MyID check. A trusted phone is exactly why. The only exception is a yellow verdict. Last, the platform writes an audit event, and sends the event login to the antifraud system of the bank. Aziz pays for the bus pass. The whole login took less time than the bus takes to arrive. To recap. The password opens the door, and it always comes first. The code through TAF proves the SIM card. The verdict scores the attempt. The phone's own face check confirms the holder. And then, a new grant. But all of this leaned on one fact: the platform already knew this phone. What if the phone is brand new, with Aziz's number and Aziz's password? Next: login from a new device.
