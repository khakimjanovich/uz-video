Imagine that a copy of the platform's database leaves the bank on a stolen disk. The thief opens the table with Aziz's verified identity. What can he read? In lesson sixteen, the platform kept Aziz's verified identity after one full proofing, with the reusable identifier from MyID next to it. This lesson shows how that record is protected: who holds its keys, who may read it, and how every read leaves a trace. First, what counts as protected. The verified identity, in all its versions: names, date and place of birth, the personal identification number, gender, citizenship, nationality, document data and registered addresses. The phone number that MyID gave. The reusable identifier, and its expiry date. And the images from the camera, but only if the bank turns image storage on. Nothing else lives in this class. Phone numbers, devices and network addresses are personal data too, but other rules handle them. Now the keys. Each identity record has its own data key. The record is encrypted with that key, and the key itself is stored only in wrapped form, locked by the installation key. The installation key never leaves the bank's Vault. When the platform must read the record, it sends the wrapped key to Vault, gets it unwrapped for that one request, and forgets it when the request ends. No part of the system keeps a decrypted copy longer than the request, and the identity never goes to a log. So the thief with the disk reads only ciphertext, and a wrapped key that he cannot open. But then, how does the platform find Aziz by his personal identification number, without decrypting every row? With a blind index. Next to the record, the platform keeps a keyed digest of the number, made with a second key from Vault: the index key. To find a person, it makes the same digest and looks it up. It is fast, it allows one active customer for each number, and without the index key the digest tells the thief nothing. Inside the gateway, only one module may touch this table: the identity module. Every other module asks it. And it answers with masked values, unless the purpose is on a short list. Here is that list. Keeping a new proofing result. The confirmation screen, on the device of the session that gave the result. The phone check. The customer lookup, with the personal identification number only. A case or a phone review, with masked values only. A compliance export, when a customer asks for his own data. The deletion job. And a verified address, when Aziz approves a sharing request. Now look at the other side: who never gets it. The bank's apps get only an identity summary, with the level and the display name, but no personal identification number, no document number, no address and no image. The bank's antifraud system, the notifications and the audit trail never get it. And a different app never gets it, except the address that Aziz chose to share. Every release is an audit event, with the reader and the purpose. Last month, an operator opened a case about Aziz. She saw only masked values: the first two and last two digits of his number, and the last four characters of his document. The audit trail recorded her, the purpose, and the time. I think this line matters more than the encryption. Encryption stops the thief with the disk, and the audit line stops the person who already has access. It also means that a later phase can show Aziz who read which data, when, and why. One more rule keeps the history honest. Identity data changes only through a refresh, which is a new full proofing. A refresh writes a new version, and keeps the old one for the configured retention time. The personal identification number is the same in every version of one customer. To recap: one protected class, a key for each record, the installation key in the bank's Vault, a blind index for search, one module at the door, masked reads by default, and an audit event for every release. One field in that record still needs a check: the phone number from MyID. It may be an old number from years ago. Does Aziz's phone number really belong to Aziz? Next: the phone check.
