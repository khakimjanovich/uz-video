How does a bank install this system on its own servers, with no setting left at a default and no secret typed into a file? The system ships as two units, installed separately: the cards unit first, because it is the card zone, then ecom, which only calls it. Each unit is one Docker Compose install with its own Vault, Postgres, Keycloak and monitoring; the Kubernetes manifests are parked, and Compose is the reference install. Every setting lives in Vault: each service's settings are rendered into environment variables, and the services read only those. Nothing has a default: a missing value stops startup, and the error names it. Opening Vault stays human: it starts with five unseal shares, any three of them open it, and each share is held by a different person. The root token is used only for setup and then revoked; any later change needs three keyholders again. Everything else is code: OpenTofu creates Vault's setup and every service's settings, and generates every password, key and certificate, with its own state encrypted by a passphrase. One procedure runs on a laptop, a dev server and production; only what the environment alone knows is typed in, once, and OpenTofu names any value that is missing or malformed. The first bank admins come from one input, at least two of them, so nobody holds the bank side alone; each sets their own password and authenticator app. A release is a tag: its images are pinned to that version, built for x86 and ARM, each with a bill of materials and build provenance. There is no deploy repository of ours: which version runs where is the bank's state, in its own Git, under its own change control. The card zone is the bank's vault room, with walls, guards, cameras and patching; the product is the safe delivered into it. So each unit ships an implementation guide: what the zone must provide, how to install and run the product, and a P C I D S S matrix of what the product does and what the bank does.
