Where does the buyer type their card number: on the shop's site, or on ours? If shops collected card numbers, every shop would need PCI DSS, and one shop's breach would leak cards. So the merchant sends the buyer to the bank's own payment page, through the one-time link it got when it created the payment. The link's token is the only credential: the database keeps only its hash, and after the configured time the link works no more. Reading the page changes nothing: it shows the website's name and logo, the amount, the order, and the cards the website accepts. The buyer types the card, and the BIN module names its scheme and bank first, so a card the website doesn't accept never gets a code. The card module checks the Luhn digit, stores the number encrypted, and asks the card's scheme, through its adapter, to send a one-time code to the cardholder's phone. Each code gets its own binding, so two payments with the same card never overwrite each other's code. The page now shows the bank, the scheme and the card's last four digits, kept in the payment's card columns, and waits for the code. The right code confirms the card through the same scheme, and the payment is ready to debit. Every attempt is counted, and committed before the scheme is asked, so a failed attempt still counts. Three cards, and three codes for each card, are allowed, and both numbers are configuration. When the last attempt fails, the page closes for good. One step runs at a time: a second click while the scheme is still answering is refused by a lock in Redis, which only its holder releases, and which outlives the slowest scheme call. Next, the moment the money actually moves: the debit.
