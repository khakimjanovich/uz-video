Where does the buyer type their card number: on the shop's site, or on the bank's? If shops collected card numbers, every shop would need PCI DSS, and one shop's breach would leak cards. So the merchant sends the buyer to the bank's own payment page, through the one-time link it got when it created the payment. The link's token is the only credential: the database keeps only its hash, and after the configured time the link works no more. Reading the page shows the website, the amount and the order, and opens a card-entry session in card-vault, the cards unit's own service. The session lists only the schemes the website accepts that have a live e POS terminal right now, speaks the buyer's language, and carries the sales point as its risk reference. The buyer types the card and the code into card-vault's frame inside the page, so ecom never sees a card number. The frame answers to one parent page only, through frame-ancestors, and its content security policy and subresource integrity let nothing run but its own two files. Those two files are the whole script inventory that PCI DSS asks for, and every load the browser blocks is reported back and logged. A card of a scheme the website doesn't accept is refused before any code is sent. When the code is right, the frame posts the card token, the masked number, the expiry, the scheme and the issuing bank to the page, and nothing more. That token travels through the buyer's browser, so ecom asks card-vault whether this payment's session is bound with that same token. Only then the payment keeps the card, by token, mask, scheme and bank, and the debit starts in the same call. Attempts belong to the session, and how many cards and codes one session allows is the caller's configured setting. Each attempt is claimed by one atomic update before the scheme is asked, so parallel posts can't pass the limit, and a refused card still counts. The last refusal ends the session, the frame tells the page so, and the page opens a fresh session, up to the configured number; past it, the payment fails. Card-vault also holds fraud limits against card testing: refused cards and codes are counted per card, per BIN, per payer address and per risk reference. Past a limit, a new card, code or session is refused before any scheme is asked, and the page says card entry is limited for now. One step runs at a time: a second click while the first is still running is refused by a lock in Redis, which only its holder releases. Next, the moment the money actually moves: the debit.
