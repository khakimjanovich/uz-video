How do you know exactly what is running inside a bank? In lesson thirty-nine, the same install ran on a laptop, a test server and production. Only the values changed, so the product itself must be exactly the same too. This lesson numbers each release, so everyone knows exactly what is running. Picture a product that always runs whatever is newest. On Tuesday, a rebuild quietly pulls a newer version nobody tested. On Wednesday, someone rolls back, pulls the newest again, and gets the same broken build. Then the bank's assessor asks: what exactly runs in your card zone, and what is inside it? Nobody can answer. A moving name can never say what runs. Think of a book. Its second edition never changes once it is printed. When you quote it, you say which edition you read, and anyone can find the same page. Releases work the same way. Each part of the system numbers its versions in three parts. The first number grows when a change breaks something callers rely on. The second grows when something is added. The third grows for a fix. So the number alone tells you how careful to be. A release is one numbered version, made once, from one exact state of the code, and never changed after. Everything is built from it, and published under its number. Each built piece carries a bill of materials: a list of every component inside it, each with its version. It also carries a record of how it was built. So the assessor's question has an answer, written on the piece itself. Every install pins its versions. A pin is one line that names the exact release a product runs. There is one line for the card zone, one for ecom, and one for the portals. Every environment runs real releases, the laptop too. So what a builder tests is exactly what the bank runs. An upgrade is four steps. Back up. Change the pinned line. Deploy. Check. The card zone goes first, before ecom, which depends on it. The release notes are read before starting: they say what changed, and whether a new value is needed. And the database only moves forward. A release can change the shape of the database, but never steps it back. So rolling back across such a change means restoring the backup taken just before. That is why the backup is always step one. Let's watch the product. An operator plans an upgrade. They look at the list of releases. Each has a plain number and its notes. They choose the newest, and read its notes first. The notes say whether a breaking change is inside, and whether the installer will ask for a new value. On the server, the operator takes the backup. Then they change one line: the card zone's pinned release, from the old number to the new one. They deploy. The services restart on the new release, in order. The health check runs: every service healthy. Only then do they do the same for ecom. Later, the assessor asks again: what is inside the card zone? The operator opens the bill of materials of one of its pieces. It lists every component inside, each with its version, and the count sits at the bottom: the answer to the question. What does this protect? It protects the bank from surprises: nothing changes unless someone changes a pinned line. It protects a rollback, because an old release is still exactly what it was. It protects the assessor's trust, because every piece can say what it contains. And it protects the data, because the backup always comes before the change. Back to the bookshelf.
