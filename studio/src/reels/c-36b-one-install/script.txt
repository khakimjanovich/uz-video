Monday, two in the afternoon. The keyholders are back at their desks, and Vault is open. In lesson thirty-eight, three of them unsealed it. Now Timur installs everything else on top of it. Across town, Bekzod, the developer who connects Malika's flower shop to the bank, runs the same install on his laptop. This lesson is about why those two installs are the same. Elsewhere, someone installed the product by hand, and has since moved on. Months later, nobody knows which values production runs with, or why the test server behaves differently. An install nobody can repeat is an install nobody understands. So the steps are identical on a laptop, a test server and production. Only the values differ, and each environment's values are written down once. A value is anything that belongs to this bank in this place: an address, a certificate, an email for alerts. The card zone has its own values, and the bank sets every one. Who may call the card zone, and which roles each caller may use. The fraud limits from lesson fourteen: how many refused tries a card, its first digits, an address or a shop may have within a window of time. How long a card entry session lives, how many tries it allows, and how long a code lives. Each is the bank's chosen value. Nothing has a default, and nothing is guessed. I think a default is a decision nobody made. The bank sets each value once for each environment, and they are kept in Vault. Order matters too. The card zone installs first. ecom then asks the card zone for its certificate, waits until it is signed, and carries on. Before anything is installed, a preflight runs. A preflight is a check of the machine before any work starts. It looks for what the install needs, such as the right tools and free ports. When something is missing, it says exactly what to fix. Then Vault is set up, and every service's settings are written from it. The services start in order, each one waiting for what it needs. A later change is just a new value, applied the same way, and only the services that use it restart. Every install ends with a health check: each service is asked whether it is ready, and answers a clear yes or no. Timur starts the card zone's installer on the fresh server. The preflight runs first. Most lines pass. One line fails, and right under it is the fix. Timur fixes it and starts again. Now everything passes. The installer asks for the release to run. Then it asks for the bank's values, one at a time. Where each door listens. Which callers may use the card zone. For each caller, the websites it serves, how long a card entry session lives, and how many tries it allows. Malika's shop is one of those websites. Then the fraud limits, the addresses for alerts, and the certificate for the payers' door. Every answer is checked as it is given. An answer in the wrong form is asked again. A certificate that does not match its key is asked again, with the reason. When every value is there, the installer says so, and how many it asked. It starts the services in order, and ends with the health check: every service healthy. Then Timur runs ecom's installer. It asks for its own values, sends its certificate request, and waits. On the card zone, the request is signed. ecom carries on, and its own health check shows every service healthy too. By evening, every value the bank runs on is written down, once, in one place. A missing value stops the install instead of being filled in. And what Bekzod tests on his laptop is the same install that runs in the bank. Next: how a release is numbered and shipped.
