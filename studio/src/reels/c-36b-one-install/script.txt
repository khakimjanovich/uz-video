How do you install the same system on a laptop and inside a bank? In lesson thirty-eight, three keyholders opened Vault. This lesson installs the whole system on top of it, the same way everywhere. Picture a product installed once, by hand, by someone who has since moved on. Months later, nobody knows which values production runs with, or why the test server behaves differently. An install nobody can repeat is an install nobody understands. Think of the cook from Lesson six. The cook follows one recipe in every kitchen. Only where the ingredients come from changes. Our install works the same way. The steps are identical on a laptop, a test server and production. Only the values differ, and each environment's values are written down once. A value is anything that belongs to this bank in this place: an address, a certificate, an email for alerts. The card zone has its own values, and the bank sets every one. Who may call the card zone, and which roles each caller may use. The fraud limits from Lesson fourteen: how many refused tries a card, its first digits, an address or a shop may have within a window of time. How long a card-entry session lives, how many tries it allows, and how long a code lives. Each is the bank's chosen value. Nothing has a default, and nothing is guessed. The bank sets them once for each environment, and they are kept in Vault. Order matters too. The card zone installs first. ecom then asks the card zone for its certificate, waits until it is signed, and carries on. Before anything is installed, a preflight runs. A preflight is a check of the machine before any work starts. It looks for what the install needs, such as the right tools and free ports. When something is missing, it says exactly what to fix. Then Vault is set up, and every service's settings are written from it. The services start in order, each one waiting for what it needs. A later change is just a new value, applied the same way, and only the services that use it restart. Every install ends with a health check: each service is asked whether it is ready, and answers a clear yes or no. Let's watch the product. An operator starts the card zone's installer on a fresh server. The preflight runs first. Most lines pass. One line fails, and right under it is the fix. The operator fixes it and starts again. Now everything passes. The installer asks for the release to run. Then it asks for the bank's values, one at a time. Where each door listens. Which callers may use the card zone. For each caller, the websites it serves, how long a card-entry session lives, and how many tries it allows. Then the fraud limits, the addresses for alerts, and the certificate for the payers' door. Every answer is checked as it is given. An answer in the wrong form is asked again. A certificate that does not match its key is asked again, with the reason. When every value is there, the installer says so, and how many it asked. It starts the services in order, and ends with the health check: every service healthy. Then the operator runs ecom's installer. It asks for its own values, sends its certificate request, and waits. On the card zone, the request is signed. ecom carries on, and its own health check shows every service healthy too. What does this protect? It protects the bank from an install nobody can explain: every value is written down, once, in one place. It protects production from a guess: a missing value stops the install instead of being filled in. And it protects testing: what works on a laptop is the same install that runs in the bank.
