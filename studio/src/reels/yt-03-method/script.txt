Where do you start designing a feature: the database, the API, or the code? It starts with the domain: the things that exist, the states they move through, and the rules that never break. First comes a one-page sketch of the whole system: the main entities, and which module owns each one. Links between modules are only IDs, never foreign keys, so a module can move out on its own later. Second comes the contract: an OpenAPI spec in the platform folder, which promises clients exactly what they can ask for. Gradle turns it into a partner API jar, and our controller must implement it, so the code can never drift from the spec. Third comes the database: a Liquibase migration creates the partner table in its own schema; its verified email, contract number and login are explained in episodes four, five and seven. The partner module has its own data source, built by the shared persistence library, and connects as a user that sees nothing but its own schema. Then the code: the controller calls the service, the service calls the repository, and a mapper turns the entity into the contract's model. A missing partner is not a crash: the service throws partner not found, and the error library answers with a problem detail, in the caller's language. Swagger UI shows the exact spec as it is written, not documentation guessed from the code. Domain, contract, database, then code: every episode follows this order.
