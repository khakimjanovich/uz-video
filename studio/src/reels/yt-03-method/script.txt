Where do you start designing a feature: the database, the API, or the code? We start with the domain: the things that exist, the states they move through, and the rules that never break. First comes a one-page sketch of the whole system: the main entities, and which module owns each one. Links between modules are only IDs, never foreign keys, so a module can move out on its own later. Second comes the contract: an OpenAPI spec in the platform folder, which promises clients exactly what they can ask for. Gradle turns it into a partner API jar, and our controller must implement it, so the code can never drift from the spec. Third comes the database: a Liquibase migration in the partner's own schema. The partner module has its own data source, and connects as a database user that sees nothing but its own schema. Then the code: the controller calls the service, the service calls the repository, and a mapper turns the entity into the contract's model. A missing partner is not a crash: the error starter returns a problem detail with the code partner not found. A unit test guards the rule, and an integration test on a real Postgres proves the partner user cannot touch the payment schema. Swagger UI shows the exact spec we wrote, not documentation guessed from the code. A k6 load test reads partners at about two thousand four hundred requests per second, with a p95 of three milliseconds. Domain, contract, database, code, and test: every episode follows this order.
