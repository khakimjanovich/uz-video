How does the merchant's server learn that a payment is paid? The shop needs to know before it ships the goods. Its server might be down for an hour, and still needs every event when it comes back, in order. It must also tell a real event from a forged one. Anyone can send a message that says paid. And there is a danger for the bank. An attacker could set their webhook address to a server inside the bank's own network, and make ecom call it. Think of a registered letter. It is sealed, so the reader knows who sent it. It goes only to a real street address. If nobody is home, the postman comes back later. And after a while, the letter is marked as returned. A webhook is that letter. When the news about a payment leaves the outbox, ecom posts it to the website's webhook address. That address is set by the merchant for each website. Every event carries its own id, the time it was sent, and a webhook signature. The signature is made with the same signing key as the merchant's API client. It follows a common open standard, so any webhook library can check it. The merchant's server checks the seal, drops events that are too old, and drops any id it has seen before. Before connecting, ecom checks the address. It must be a secure address. It must lead only to the public internet. And it is checked again at the very moment of connecting, so it cannot change in between. Redirects are not followed. This guard stops server-side request forgery: a trick where someone makes a server call places it should never reach. A delivery succeeds only when the merchant's server answers with success. Anything else is tried again, waiting longer each time. A payment's later events wait behind an earlier one, so they stay in order. After the bank's chosen time, an event that never got through is marked undelivered. The merchant can then ask for it again. Payment links get no webhooks, because there is no server behind them. Now watch the product. In the merchant portal, open a payment. Below its calls to the card scheme is a section called webhooks. Each event shows its type and its status. Here it says delivered, after one attempt, with the last answer from the merchant's server. Now take the merchant's server offline, and make a new payment. Its event says retrying, with the time of the next attempt and the last answer, which is no answer. A later event for the same payment says waiting for an earlier event. While an event is still retrying, there is no button to send it again. In the end, it says undelivered. The hint says the server never answered with success, and asks the merchant to fix it, then send the event again. The merchant brings the server back, and presses send again. A short note says it is queued and goes out within seconds. The status turns to delivered. Open a payment made from a link, and the section says no webhook was sent: the website has no webhook address, or it is a payment link. What does this protect? The signature protects the merchant from a forged paid. The retries protect the merchant from losing news during an outage. The order protects against seeing refunded before paid. And the address guard protects the bank's own network from its own webhooks. So back to the registered letter. Sealed, sent only to a real address, and tried again until it arrives.
