Saturday, two in the afternoon. Bekzod's hosting company takes Malika's server down for an hour of maintenance. In that hour, the shop sells six bouquets. Malika ships nothing until her server hears paid, so all six wait. In lesson twenty-nine, every payment's news waited in the outbox for the relay, and in lesson twenty-four, Bekzod's server signed what it sent to the bank. This lesson delivers that news the other way, signed by the bank, to Bekzod's server. When the server comes back, it needs every event it missed, in order. It must also tell a real event from a forged one, because anyone can send a message that says paid. And there is a danger for the bank itself. Someone who signs up as a merchant could set their webhook address to a server inside the bank's own network, and make ecom call it. The news travels as a webhook. When a payment's news leaves the outbox, ecom posts it to the website's webhook address. That address is set by the merchant for each website. Every event carries its own id, the time it was sent, and a webhook signature. The signature is made with the same signing key as the merchant's API client. It follows a common open standard, so any webhook library can check it. Bekzod's server checks the seal, drops events that are too old, and drops any id it has seen before. Before connecting, ecom checks the address. It must be a secure address. It must lead only to the public internet. And it is checked again at the very moment of connecting, so it cannot change in between. Redirects are not followed. This guard stops server side request forgery, a trick where someone makes a server call places it should never reach. I would never ship webhooks without this guard, because without it, the bank's own webhooks become a way into the bank. A delivery succeeds only when the merchant's server answers with success. Anything else is tried again, waiting longer each time. A payment's later events wait behind an earlier one, so they stay in order. After the bank's chosen time, an event that never got through is marked undelivered. The merchant can then ask for it again. Payment links get no webhooks, because there is no server behind them. Here is that Saturday in the merchant portal. On a normal day, Malika opens a payment. Below its calls to the card scheme is a section called webhooks. Each event shows its type and its status. Here it says delivered, after one attempt, with the last answer from her server. Now she opens a payment from the maintenance hour. Its event says retrying, with the time of the next attempt and the last answer, which is no answer. A later event for the same payment says waiting for an earlier event. While an event is still retrying, there is no button to send it again. Suppose the maintenance runs long, past the bank's chosen time. The event says undelivered. The hint says the server never answered with success, and asks the merchant to fix it, then send the event again. Bekzod brings the server back, and Malika presses send again. A short note says it is queued and goes out within seconds. The status turns to delivered, and the bouquets ship. One last case. Open a payment made from a link, and the section says no webhook was sent: the website has no webhook address, or it is a payment link. So a forged paid never ships a bouquet. An outage loses no news. Refunded never arrives before paid. And the bank's own network stays out of reach of its own webhooks. Next: payments without a website.
