Thursday, eleven at night. Somebody opens the marketplace web page, types Aziz's phone number, and starts to try passwords from a leaked list, one after another. Aziz is asleep. His password is in the platform. So how does a platform keep a password that it must check, but can never read? In lesson ten, Aziz typed his password two times, and the platform made him a customer. Lessons eleven and twelve guarded the code that comes after the password. This lesson opens the box that holds the password itself. First, where it lives. Aziz has one password for every app of the bank, so the platform keeps exactly one row for him, in Postgres. It belongs to the customer gateway, not to Keycloak. Keycloak never sees the password at all. Why not let Keycloak keep it? Because the gateway must check the password before it sends any code. If Keycloak held it, the code would go out first, and the password would travel to Keycloak at every login. Now, what is in the row. Not the password. The gateway runs the password through Argon2id, a memory-hard hashing function. Memory-hard means that every single check needs a real block of memory and real time. For the gateway, that is one check per login. For an attacker with a stolen copy of the table, every guess costs the same, so millions of guesses become very slow and very expensive. Before the hashing, the gateway adds a salt: random bytes, new for each password. So two customers with the same password still get two different digests, and no table of ready answers works. The row keeps one string: the name of the algorithm, its settings, the salt and the digest. The settings come from the configuration of the installation, not from the code. Older digests are never kept, and only the login module may read the row. Older functions like bcrypt were not chosen, because they are not memory-hard. Back to Thursday night. Every login starts with the password, before a code, before a new-device request, before a web approval. The gateway compares the digests in constant time. And here is a detail I really like. When the number belongs to nobody, the gateway still runs a check, against a fixed dummy digest. The answer is the same, wrong number or password, and it takes the same time. So the stranger cannot even learn whether a customer exists. Each wrong password adds one to a counter in the row. The same transaction writes an audit event and an event for the bank's antifraud system. At the configured limit, the gateway locks password login for the configured time. Aziz gets a message by SMS and by push: password login locked. The stranger gets one answer: Too many wrong passwords. Try again at the given time, or reset the password. On Friday morning, Aziz opens the mobile bank. It works. A lock is not a block. His sessions keep running, because renewing a session needs no password. The lock ends by itself after the lock time, or after a password reset, which lesson thirty explains. But the message worries Aziz, so he changes his password. In the mobile bank, he types the current password, then the new one, and then the new one again. The same rules as at registration apply: long enough, not on the breached list, no phone number inside. A wrong current password would count as one more wrong entry. In one transaction, the platform writes the new digest and removes the old one. The counter goes to zero and the lock ends. The events go to the outbox in the same transaction, so nothing is half done. Then every other session of the same or a lower rank than the one he used ends. His marketplace session on the laptop ends at once. He logs in there again with the new password. And a message goes out: password changed. A few things never happen to a password. The platform never shows it, returns it, logs it or sends it. The app masks it on the screen and does not keep it. And it is not the app PIN, which only opens the app on his phone. To recap. One row for each customer, with a slow, salted Argon2id digest. The password is checked first, in constant time, even for a number that belongs to nobody. Wrong guesses lock password login, but they block nothing else. A change ends the weaker sessions. Aziz now has a number, a password and a session, all at level one. The bank knows his phone, but not yet the person. To prove the person, the platform must call MyID. But before it may call MyID, what must Aziz agree to? Next: consent.
