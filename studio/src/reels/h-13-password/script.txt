Thursday, eleven at night. A script calls the API of the platform with Aziz's phone number, and tries passwords from a leaked list, one after another. Aziz is asleep. His password is in the platform. So how does a platform keep a password that it must check, but can never read? On Sunday, Aziz typed that password two times, and became a customer. On Monday at the café, his login began with it, before any code. Behind that first step is a box that holds the password itself. First, where it lives. Aziz has one phone number, and the number has one password. So the platform keeps exactly one row for that number, in Postgres. The row belongs to the customer gateway, not to Keycloak. Keycloak never sees the password at all. Why not let Keycloak keep it? Because the gateway must check the password before it sends any code. If Keycloak held it, the code would go out first, and the password would travel to Keycloak at every login. Now, what is in the row. Not the password. The gateway runs the password through Argon2id, a memory-hard hashing function. Memory-hard means that every single check needs a real block of memory and real time. For the gateway, that is one check per login. For an attacker with a stolen copy of the table, every guess costs the same, so millions of guesses become very slow and very expensive. Before the hashing, the gateway adds a salt: random bytes, new for each password. So two customers with the same password still get two different digests, and no table of ready answers works. The row keeps one string: the name of the algorithm, its settings, the salt and the digest. The settings come from the configuration of the installation, not from the code. The platform keeps no older password, and only the login check of the gateway may read the row. Older functions like bcrypt were not chosen, because they are not memory-hard. Back to Thursday night. Every login starts with the password, before any code goes out. The gateway compares the digests in constant time. And here is a detail worth copying. When the number belongs to nobody, the gateway still runs a check, against a fixed fake digest. The answer is the same, wrong number or password, and it takes the same time. So the script cannot even learn whether a customer exists. Each wrong password adds one to a counter in Valkey, for this number. The gateway also writes an audit event and tells the bank's antifraud system. At the configured limit, the gateway sets a lock in Valkey, for the configured time. Now password login for this number is locked. Aziz gets an SMS and a push: password login locked. The script gets one answer: too many wrong passwords, try again later. When the time is over, the lock ends by itself. On Friday morning, Aziz reads the message and opens the mobile bank. It works. A lock is not a block. His session keeps running, because the renewal of a session needs no password. Leaked lists are also why, at registration, the platform refuses each password from its list of common and breached passwords. A few things never happen to a password. The platform never shows it, returns it, logs it or sends it. The app masks it on the screen and does not keep it. And it is not the app PIN, which only opens the app on his phone. Now a check for you. Suppose the script types a number that belongs to nobody: does the answer come faster? No: the gateway checks the fixed fake digest, so the answer and its time are the same as for a wrong password. One row for each number, with a slow, salted Argon2id digest. The password is checked first, in constant time, even for a number that belongs to nobody. Wrong guesses lock password login, but they block nothing else. Aziz has a number, a password and a session, all at level one. The bank knows his phone, but not yet the person. Lesson twelve starts on a Saturday, when Aziz wants to send money to his mother.
