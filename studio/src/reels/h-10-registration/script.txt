On Sunday evening, Aziz wants to save a pair of running shoes in the marketplace, on his laptop. The web page asks for his phone number. Nothing more. So what happens between that phone number and a customer who can use every app of the bank? In lesson nine, the apps learned to call the heeyID API through its contract, and only the master app got the MyID and TAF parts. This lesson follows the first call of that contract: the registration, from a phone number to level one. Aziz types his number and taps Continue. The marketplace sends the app, the number, the language of the journey and a short description of the device. The request also carries its network address. The platform checks three facts. The number is a real mobile number of Uzbekistan. The app is active. And no limit is reached, which is the subject of lesson eleven. Then the platform opens a registration record, in the state Started. From now on, every text and every code message to Aziz is in his language. Next, the platform makes a one-time code. The code is random. It never comes from the number, the time or the device. The platform keeps it only as a digest, so even the database cannot say the code back. The marketplace gets the lifetime of the code and the number of resends that remain. It never gets the code. Who sends the SMS? Here the app decides. The marketplace web profile is a side app, and side apps do not contain the TAF part. The TAF check works only when TAF itself sends the code to the phone that types it. So in a side app, on a phone or on the web, the bank's own SMS service always sends the code. Aziz reads the code on his phone and types it on his laptop. The platform compares it with the digest. They match, so the record moves to Number verified, and the code is void. There is no verdict on the web. The audit event simply says that the source was web. Now one rule that I think every identity team should copy. Until the number is verified, the platform makes nothing for it: no consent, no device record, no session. A request that tries gets one answer: number not verified. Next, the platform looks up the number. It belongs to nobody, so this is a new person. The marketplace asks Aziz for a password, and then for the same password a second time. Aziz types two different words by mistake, and the platform refuses: the two entries are not the same. He tries again. This time the password is long enough, it is not on the list of common and breached passwords, and it does not contain his phone number. Nobody asks him for a symbol or a capital letter. Lesson thirteen shows how the platform keeps it. Now four things appear at once. A customer at level one. An app account in the marketplace. A device record for the browser, which can never become trusted. And a session for this browser. The registration record is now Onboarded. The marketplace needs only level one to keep a wish list, so Aziz uses it at once. On Monday morning, Aziz installs the mobile bank on his phone, and types the same number. This time the code goes another way. The mobile bank is the master app, so the platform sends the code through TAF. TAF sends the SMS, and its part inside the app checks that the code arrived on this phone, with this SIM card. If TAF does not answer, the bank's SMS service sends the code instead, and lesson twelve shows what that costs. Aziz types the code, and the number is verified again. But now the number belongs to a customer: Aziz himself, from Sunday. So this is not a registration. The platform does not show the existing account. It asks for the same password, the one from Sunday. Then it continues as a login from a new device, and it adds an app account for the mobile bank. Still one person, one number, one password. What if the person on Monday did not know that password? Then the only way forward is a password reset, never a second account. And if the number belonged to a blocked customer, the journey stops with one sentence: Please contact the bank. One more case. A registration that never reaches level one does not wait forever. After the configured time, the record expires. The platform deletes its data and keeps only the audit events. A new try starts from the beginning. To recap. The app sends the number. The platform opens a record, and makes a random code that it keeps only as a digest. The master app gets its code through TAF, and every side app through the bank's SMS service. A verified number then becomes a new customer at level one, or a login for a customer who already exists. But look at Sunday evening again. The code went to a number that anyone can type. What stops a stranger from asking for codes all night, or from guessing one? Next: codes and limits.
