It is a quiet Tuesday in the data centre of the bank, and the platform team sets up heeyID for the first time. One line is missing from the configuration: the lifetime of a one-time code. What should the platform do: guess a number, or stop? In lesson five, each app got its own required level, and each token its own lifetime. This lesson shows who sets values like these, where they live, and how they change. Many systems would guess. Somewhere in the code there is a constant, and the constant wins, quietly. In heeyID, the code has no default value at all. I think a default hidden in the code is a decision that nobody signed. Nobody sees it, nobody approves it, and nobody can say when it changed. So the defaults live in one place: the OpenTofu configuration of the installation. OpenTofu is the tool that describes the installation as code. Its catalogue holds a value for each policy in the requirements, and the default texts for consent, terms and notifications, in four languages. At setup, the platform reads this catalogue and writes it as version zero. The proposer of version zero is the product, and each row has a mark that says: this is still the default. If one value is missing, the setup stops, with a clear error that names the value. So on that Tuesday, the platform team sees the missing code lifetime in the first minute, not in a complaint from a customer a month later. There is a second gate before the first customer. The installation does not start its service until the bank has at least one active app with a required level. Until then, every journey answers: the service is not available. Two kinds of values sit in that configuration. Policies are settings of the bank: code lifetimes, attempt limits and waiting times. Installation keys belong to one zone: the MyID host, the zone itself, whether test customers are allowed, the breaker values and the access token lifetime. The bank can change a policy in the administrator panel. Nobody can change an installation key there. Now a policy changes. Months later, Malika, a security administrator of the bank, wants a shorter lifetime for one-time codes. She opens the panel, and makes a proposal. The proposal shows the current value, the new value and her reason. The value does not change yet. A second security administrator must approve it, and Malika cannot approve her own proposal. This is maker-checker: one person makes a change, and a different person with the same role checks it. When her colleague approves, the policy gets a new version, with the proposer, the approver, the times and the reason. If the colleague rejects it, the rejected proposal stays, with its reason. And if a new value turns out wrong, a staff user with that role can propose an earlier version again. Texts follow the same path, with the Compliance role in place of the security administrator. The platform also checks each value itself. It refuses zero, a negative number, a wrong unit, a minimum match confidence below the threshold, and a dormancy period that is too long. A typo cannot become a policy. The panel shows one more thing: which values are still the product default. So the bank can see, on any day, which decisions it made itself, and which it took from the product. Back to the missing line. The setup stopped, the team added the value, and version zero was complete. Malika's change became version one, with two names on it. Every value has a source, a version and an owner. That is why this course says the configured time or the configured limit, and never a number. The number belongs to the bank. To recap: there is no default in the code. The defaults and the texts come from the OpenTofu configuration, as version zero. A missing value stops the setup. Policies change in the panel with maker-checker, and installation keys do not. Some of those values are timeouts: how long heeyID waits for MyID, TAF or the SMS service. So what happens when one of them is slow, or down? Next: adapters.
