Suppose the platform team of a bank sets up heeyID for the first time, in a quiet data centre. One line is missing from the configuration: the lifetime of a one-time code. What should the platform do: guess a number, or stop? Lesson three gave each bank its own installation, inside its own perimeter, in two zones. Each installation needs its own values, and this lesson shows where they come from and how they change. Many systems would guess. Somewhere in the code there is a constant, and the constant wins, quietly. In heeyID, the code has no default value at all. A default hidden in the code is a decision that nobody signed. Nobody sees it, nobody approves it, and nobody can say when it changed. So the values live in one place: the OpenTofu configuration of the installation. OpenTofu is the tool that describes the installation as code. Its catalogue holds one value for each policy, and the default texts for consent, terms and notifications, in four languages. At setup, the platform reads this catalogue and writes it as version zero. The proposer of version zero is the product, and each row has a mark that says: this is still the default. If one value is missing, the setup stops, with a clear error that names the value. So the platform team sees the missing code lifetime in the first minute, not in a complaint from a customer a month later. There is a second gate before the first customer. The installation does not start its service until the bank has at least one active app with a required level. Until then, every journey answers: the service is not available. Two kinds of values sit in that configuration. Policies are the rules of the bank for each customer journey: code lifetimes, attempt limits and waiting times. Installation settings belong to one zone: the hosts, the zone itself, whether test customers are allowed, the call timeouts, the breaker values and the access token lifetime. A policy has versions, a history and the default mark. An installation setting is how one zone runs, and a change needs a new deployment. Later, the bank wants a shorter lifetime for one-time codes. Nobody changes it in the administrator panel, because the panel changes no policy and no setting. The platform team changes one line in the OpenTofu configuration, and applies it. The platform checks the new value before it uses it. It refuses zero, a negative number, a wrong unit, or a value outside its allowed range. A typo cannot become a policy. A valid value becomes a new version of the policy, and the earlier version stays in its history. Texts follow the same path: a new consent text comes from the configuration, as a new version. Back to the missing line. The setup stopped, the team added the value, and version zero was complete. The shorter code lifetime became version one, with its time and its source. Every value has a source, a version and an owner. That is why this course says the configured time or the configured limit, and never a number. The number belongs to the bank. Check yourself: the bank wants heeyID to wait longer for TAF, so where does that change go? It is a call timeout, so it is an installation setting: the platform team changes it in the configuration of that zone, with a new deployment. There is no default in the code. The defaults and the texts come from the OpenTofu configuration, as version zero. A missing or a wrong value stops the setup. Policies and installation settings change only in the configuration, never in the panel. Some installation settings are timeouts: how long heeyID waits for MyID, TAF or the SMS vendor. Lesson five shows what heeyID does when one of them is slow, or down.
