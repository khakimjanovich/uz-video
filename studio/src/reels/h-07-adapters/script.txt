Suppose Aziz is at the MyID step, on the way to his first transfer. The mobile bank asks heeyID to open his MyID check. At that minute, MyID starts to answer slowly, and then not at all. Aziz looks at a spinner. What happens to him, and what happens to the platform? Lesson three named the services outside the bank, and lesson four gave the configuration of the installation. Here you see how the platform talks to those services, and what it does when one of them stops answering. Start in the middle, with the core of heeyID. The core holds the rules: registration, proofing, devices and login. The core itself has no input and no output. It never opens a connection, and it never calls MyID. When it needs something from outside, it calls a port. A port is a door in the words of the rules: open a proofing session, send a code, send a push. Behind each port is an adapter: the part that talks to one real service. heeyID has four of them for the outside world: MyID, TAF, SMS and push. The TAF adapter calls the TAF agent inside the bank network. The other three go out through the egress proxy. Each adapter runs as a unit of its own, and only the customer gateway and the workers call it. Now the tests. Each port has one real adapter, and no second version for the tests. For the tests, a simulator takes the place of the outside service itself. It speaks the same API as MyID, TAF, the SMS vendor or the push service. It gives every answer that the contract allows: success, each failure reason, a timeout and a service that is down. So the real adapter runs in every acceptance test, with no internet. Each night, one more run goes against the MyID test environment. A team that tests only against the real service tests only the good days. The simulator brings the bad days into every run. Now the walls around each call. Each outgoing call has a timeout: how long the adapter waits for an answer. Each adapter also has a breaker. After a configured number of failures in a row, the breaker opens. While it is open, calls fail at once, with no waiting. A test call goes to the service at a configured interval, and the breaker closes when the service answers again. While the breaker is open, operations get an alert: a dependency is down. The timeouts and the breaker values are installation settings, like the MyID host in lesson four. The panel cannot change them, and a change needs a new deployment. And now the most important rule: each outside service has one fixed behaviour when it is down. The adapter makes that behaviour impossible to bypass. A timeout always gives one plain answer, never a raw error that each caller reads in its own way. MyID is down: the customer sees that the service is temporarily not available. The customer stays at the current level, and the attempt does not count against the limits. Nothing runs later in the background, so the customer starts the check again. TAF is down: the code goes through the SMS service of the bank, and the attempt is not scored. One refusal is not an outage: when the state services portal names another bank as the trusted bank, no code goes by SMS. The SMS vendor is down: a code that needs an SMS cannot go now. The notifications wait in Kafka, and go again later. The push service is down: the notifications go by SMS only. Back to Aziz and his spinner. The MyID adapter waits for its timeout, then gives its plain answer: the provider is not available. Aziz sees a short message, and his level does not move. His attempt does not count. MyID fails for the next customers too, so the breaker opens. Now they get the same answer at once, with no spinner. When MyID answers the test call again, the breaker closes, and Aziz starts his check again. Two more rules keep the adapters safe. First, no adapter writes a request body or a response body to a log. It writes the reference, the outcome and the time that the call took. Second, hosts, ports and credentials come only from the installation configuration and Vault, never from the code. Each adapter holds only its own credential. Now a check: TAF stops answering while a customer registers, so how does the code reach him? Through the SMS service of the bank, and that registration is not scored. The core of heeyID has no input and no output. Four ports, four adapters, and a simulator for each outside service. A timeout and a breaker on every call, and one fixed behaviour for each outage. So Aziz waits a few seconds, not forever. Each adapter holds one secret: the MyID credential, the TAF client secret, the SMS vendor login and the push credential. Lesson six shows where those keys live, and who holds them.
