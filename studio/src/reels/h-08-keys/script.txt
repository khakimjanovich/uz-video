Suppose a backup copy of the heeyID database leaves the bank on a disk. Nobody should have taken it. On it are the customers of the bank: names, passport data, addresses and phone numbers. Aziz is one of them. What can the person with the disk read? Lesson five showed the adapters that talk to MyID, TAF, the SMS vendor and the push service. Each adapter takes its credential from Vault. Now Vault opens, and the keys inside it answer the question of the disk. Vault is a safe for keys, and it runs inside the bank. Each zone gets its own new Vault. The security team of the bank holds the keys that unlock it. The vendor that wrote heeyID never sees one of them. This is the line in the design that matters most: the bank keeps the keys. Vault holds nine kinds of keys for each zone. Three of them lock what the thief wants to read. First, the verified identity of Aziz: his names, passport data, personal identification number and address. The platform never encrypts these values itself. It sends each value to Vault, and Vault gives back a sealed value. This is encryption inside Vault: the key that seals the value never leaves Vault. No key is stored next to the record, only the sealed value. To read the record, the platform sends the sealed value back to Vault. Vault opens it for this one request, and the platform then forgets the clear value. Each sealed value is also bound to its place, so a value copied into a different record does not open. Vault also records each time it opens a value. On the disk, the thief has only sealed values, and nothing on the disk opens them. Second, search. The platform must find a customer by his personal identification number, among millions of customers. But that number is encrypted, so the platform cannot compare it. So it also keeps a blind index: a fingerprint of the number that Vault makes with a secret index key. The same number always gives the same fingerprint, so an exact search still works. A fingerprint never gives back the number. Without that key, nobody can make a fingerprint at all. Third, the one-time codes. The platform keeps each code only as a fingerprint, and lesson nine shows the rules for codes. A code has only a few digits, so a thief can try every possible code in a moment. That is why each fingerprint mixes in a pepper: a secret from Vault that is never on the disk. Without the pepper, all those tries give nothing. The other six kinds of keys do different work. One key seals the audit trail, so that a changed record shows, and lesson twenty-one shows it. Keycloak signs each token with its own keys, and a secret from Vault encrypts those keys in its database. The credentials of the adapters from lesson five live here too. Three more kinds work only between the units of the platform, such as their certificates. No key is ever in the code, in a log, or in an app on a phone. The passwords on the disk need no key at all. The platform keeps only a slow, salted fingerprint of each password, and lesson eleven shows it. There is no key to steal, because there is nothing to decrypt. Keys also grow old, and the bank sets how often each one changes. When the identity key changes, the platform asks Vault to seal the values again, in the background. Back to the disk. The thief can read the phone number of Aziz, and a few masked parts, such as the last four digits of his document. He cannot read the name, the passport data, the address or the full identification number of Aziz. Every key that could open them stays in the Vault of the bank. For the identity of Aziz, the disk is only lost hardware. Suppose the thief also guesses the personal identification number of Aziz. Can he use that guess to find a record on the disk? No: without the index key inside Vault, he cannot make the fingerprint, so his guess matches nothing. One Vault for each zone, inside the bank, and the bank holds the keys that unlock it. Encryption inside Vault seals each identity, a blind index finds a number without showing it, and a pepper makes the code fingerprints useless to a thief. No key sits in the code, in a log, or on a phone. The mobile bank holds no key, yet it calls heeyID at each step of the journey of Aziz.
