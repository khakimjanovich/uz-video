A backup copy of the heeyID database leaves the bank, on a disk that nobody should have taken. On it are the customers of the bank: names, passport data, addresses and phone numbers. Aziz is one of them. What can the person with the disk read? In lesson seven, each adapter held a secret, and the platform kept passports encrypted. This lesson shows where every key lives, and why the disk is worth so little. All the keys of heeyID live in Vault, and the Vault belongs to the bank. Each zone has its own new Vault, and the security team of the bank keeps the keys that unseal it. The vendor never sees one of them. I think this is the line in the design that matters most: the bank keeps the keys. Six kinds of keys sit there. Walk across the disk, and meet them one by one. First, the verified identity of Aziz: his names, his document data and his addresses. His record has its own data key, and that data key encrypts the record. The data key is stored next to the record, but wrapped: the installation key-encryption key encrypts it. The key-encryption key never leaves Vault. To read the record, the gateway sends the wrapped data key to Vault, gets it back unwrapped for this one request, and then forgets it. This is envelope encryption. On the disk, the thief has records and wrapped data keys, and no way to open them. And Vault records each time a key is unwrapped. Second, search. An operator must find Aziz by his exact personal identification number, among all the rows. But the number is encrypted. So the platform keeps a blind index: a keyed hash of the number, made with the installation index key. The same number always gives the same index, so an exact search works. Without the index key, the thief cannot even test a guess. The same key makes the digest that binds a session to its device. Third, the one-time codes. heeyID keeps a code only as a digest, and the digest mixes in a secret pepper from Vault. A short code is easy to guess, so a plain digest of it is easy to reverse. With the pepper in Vault, the thief cannot even check a guess. Fourth, the audit trail. Each audit event is chained to the event before it with an HMAC, under the audit key. Change one event, and the chain breaks. A daily verifier checks the chain, and raises an alert at each break. Fifth, the token signatures. Keycloak signs each token with the realm keys. They sit in the Keycloak database, encrypted with a secret from Vault. Sixth, the credentials of the outside services: the MyID credential, the TAF client secret, the client certificates of the adapters, and the push credential. Each credential goes only to the adapter that uses it. The push credential, for example, arrives as a file for the push adapter, and for nothing else. None of them is ever in the code, on a phone, or in a log. And the passwords? They are not encrypted at all, on purpose. heeyID keeps only a slow, salted password hash, and a hash cannot be reversed. There is no key to steal, because there is nothing to decrypt. Keys also age. Each key has a rotation period, and the bank sets it. When the key-encryption key rotates, its old versions stay for unwrapping, and the platform wraps the data keys again in the background. Old audit keys stay too, so old chains still verify. Each key has an owner who approves its change: the security team of the bank, or its platform team. Back to the disk. The thief has encrypted records, wrapped data keys, blind indexes, code digests, password hashes and a signed audit chain. Every key that could open them stays in the Vault of the bank. The disk is a loss of hardware, not a loss of identities. To recap: one Vault for each zone, in the bank. Six kinds of keys: the key-encryption key, the index key, the code pepper, the audit key, the realm keys, and the credentials of the outside services. Envelope encryption for identities, a blind index for search, and digests for codes and passwords. The keys never leave the bank, and they never reach a phone. But the apps of the bank still keep something on the phone, and still call heeyID. What may an app keep, and how does it talk to heeyID? Next: the API contract.
