Which e POS terminal does the processing center expect each debit to come through? It only accepts debits from e POS terminals it already knows: a MID and a TID it issued. So the e POS module keeps a registry: for each website and card scheme, one merchant ID and one terminal ID. Uzcard and Humo payments can use different e POS terminals for the very same website. An e POS terminal is registered only for a website that exists and accepts that card, and the check fails closed. The database allows one live e POS terminal per website and card, and a merchant and terminal ID pair is never issued twice. A Uzcard e POS terminal is also registered at Uzcard's SV-Gate, terminal add and then terminal check, and it is kept only if Uzcard accepts it, so a retry is always safe. Suspend and resume stay in our registry, because SV-Gate has no method to pause a terminal, and a revoked one never comes back. Revoking a Uzcard e POS terminal removes it from SV-Gate first, and if Uzcard refuses or stays silent, nothing changes. Admins check any Uzcard e POS terminal at SV-Gate, terminal check and terminal get side by side, and register one that SV-Gate never got. Every change is written to an audit log: who, what, and why. Before every debit, the payment module asks for the live e POS terminal, and no e POS terminal means no debit. The e POS module also lists a scheme's active and suspended terminals, so the card module can reconcile each one with Humo. Admins find any e POS terminal by website, card scheme, or status, or by part of its merchant or terminal ID, and open it to see its history and act on it.
