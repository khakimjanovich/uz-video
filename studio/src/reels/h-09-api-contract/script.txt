Monday morning, in the mobile bank team. Jasur, an iOS developer, gets his task: connect the app to heeyID. He searches for the heeyID SDK, a package that he can add with one line. There is none. So how does a team build against heeyID with no SDK? In lesson eight, every key stayed in the Vault of the bank, and none reached a phone. This lesson shows what reaches the apps instead: a contract, a guide, and a short list of things that an app may keep. First, why there is no SDK. The teams of the bank build the apps of the bank. An SDK from heeyID would add work before the first release, and a second release train for every app. I think no SDK is the honest choice for a first release: the contract is the product, and each team owns its own code. So heeyID gives three things. The REST API. The OpenAPI contract that describes it. And an integration guide with the rules for the apps. The contract describes every call: the path, the request, the answer and the errors. There is one call for each step: start a registration, verify the code, set the password, log in, approve a login, give consent, open a proofing session and renew a session. Each request carries a correlation identifier, and after registration also the device identifier. Each error has one shape: a code, a reason key, a message for the customer, and whether a retry is allowed, and after how long. The codes are the error outcomes of the requirements, one to one. So the app of Jasur never reads a sentence to find out what went wrong. It reads the code, and shows the message. Then come the SDKs that do exist. The bank adds the MyID SDK and the TAF SDK to the master app, and only to the master app. MyID runs as a native check inside the app. The backend opens the session, and the customer never leaves the app: no web view, and no web frame. The MyID credential never goes to the phone. Each app also gets the push SDK of the bank, to receive the wake-up signals. Now the guide. Its most important page is a table: what an app can keep, and where. The device identifier, in the storage that the Keychain or the Keystore protects. The refresh token, in the Keychain, or in storage that the Android Keystore protects. The access token and the identity summary, in memory only, until they expire or the app closes. An approval request, in memory and on the screen, until Aziz answers it. The push token. The app PIN, only as a slow, salted hash, on the device. And the language. Then the other column: what an app never keeps. The password. The MyID credential. The MyID result code, after its one upload. The personal identification number. Document data, addresses and images. A one-time code, after Aziz types it. A limit that the gateway uses. And biometric data. The row about limits matters. An app may show a counter, for comfort. But the platform applies every limit itself, on the server. A limit in the app is only a convenience, never a control. Now be honest about the edge of this design. heeyID cannot enforce these rules inside an app. It cannot look into the Keychain on the phone of Aziz. So the guide gives the rules, and the API tests keep the apps correct. Each app is a client of the contract, and nothing more. Back to Jasur. By Wednesday, his app calls the contract, keeps the device identifier in the Keychain and the access token in memory, and shows the errors by code. He adds the MyID and TAF SDKs, and nothing from heeyID. When the contract changes, the OpenAPI file shows the change first. To recap: there is no heeyID SDK in this release. There is the REST API, the OpenAPI contract and the integration guide. The MyID and TAF SDKs are only in the master app. There is a short list of what an app may keep, and a longer list of what it never keeps. And the server applies every limit. With these foundations in place, Aziz can type his phone number for the first time. What happens between that number and level one? Next: registration.
