Suppose Jasur, an iOS developer in the mobile bank team, gets his task: connect the app to heeyID. He searches for the heeyID SDK, a package that he can add with one line. There is none. So how does a team build against heeyID with no SDK? Lesson six kept every key in the Vault of the bank, and no key reached a phone. This lesson shows what reaches the mobile bank instead: a contract, a guide, and a short list of things that the app may keep. First, why there is no SDK. The bank's own team builds the mobile bank. An SDK from heeyID would add more work, and a second release train beside the app. No SDK is the honest choice: the contract is the product, and each team owns its own code. So heeyID gives three things. The REST API. The OpenAPI contract that describes it. And an integration guide with the rules for the app. The contract describes every call: the path, the request, the answer and the errors. There is one call for each step: start a registration, verify the code, set the password, log in, give consent, open a proofing session, set the app PIN and renew a session. Each request carries a correlation identifier, and after registration also the device identifier. Each error has one shape: a code, a reason key, a message for the customer, and whether a retry is allowed, and after how long. Each code names one outcome of the product, one to one. So Jasur's app never reads a sentence to find out what went wrong. It reads the code, and shows the message. Then come the SDKs that do exist. The bank adds the MyID SDK and the TAF SDK to the mobile bank. MyID runs as a native check inside the app. The backend opens the session, and the customer never leaves the app: no web view, and no web frame. The MyID credential never goes to the phone. The mobile bank also gets the push SDK of the bank, to receive the wake-up signals. Now the guide. Its most important page is a table: what the app can keep, and where. The device identifier, and the identifier of a running registration or login, in the storage that the Keychain or the Keystore protects. The refresh token, in the Keychain, or in storage that the Android Keystore protects. The access token and the identity summary, in memory only, until they expire or the app closes. The push token. The app PIN, only as a slow, salted hash, in the Keychain or the Keystore. And the language. Then the other column: what the app never keeps. The password. The MyID credential. The MyID result code, after its one upload. The personal identification number. Document data, addresses and images. A one-time code, after Aziz types it. A limit that the gateway uses: the app may show a counter, but the server applies every limit. And biometric data. Now be honest about the edge of this design. heeyID cannot enforce these rules inside an app. It cannot look into the Keychain on Aziz's phone. So the guide gives the rules, and the API tests keep the app correct. The mobile bank is a client of the contract, and nothing more. Back to Jasur. In the end, his app calls the contract, keeps the device identifier in the Keychain and the access token in memory, and shows the errors by code. He adds the MyID and TAF SDKs, and nothing from heeyID. The contract lives apart from the platform code, so every team reads the same file. When the contract changes, that file shows the change first. Check yourself: Aziz types his password in the mobile bank, so may the app keep it for next time? No: the password is on the never list, so the app sends it once and forgets it. There is no heeyID SDK. There is the REST API, the OpenAPI contract and the integration guide. The MyID and TAF SDKs live in the mobile bank. There is a short list of what the app may keep, and a longer list of what it never keeps. With these foundations in place, Aziz can type his phone number for the first time. Lesson eight follows that number, from the first code to level one.
