Tuesday morning, Bekzod sits down to connect Malika's website to the bank, and Malika sends him a message: just use my password, it's easier. It is easier, for about a month. In lesson eighteen, two admins switched Malika's company on, and in lesson one, the shop's server asked ecom to create each payment, and this lesson gives that server a login of its own. Her password in a server's settings ends up in a shared code store. When Bekzod moves on, Malika's own login has to change. And every request the server ever makes looks like Malika clicking buttons. I will say it plainly: a server should never log in as a person. So Bekzod opens API clients in the merchant portal. Yesterday, before the company was switched on, this page had no button at all. It said "API clients open when you are live", and explained that two bank admins must activate the account first. Only an active merchant can create or rotate an API client. Today the page explains that the merchant's servers use these to get access tokens. Bekzod clicks New client. An API client is a login for a machine, not for a person. A window opens: "Your new API client". It shows the client id, like a username, and the client secret, like a password that only the machine knows. Above them is a warning: this is the only time you will see this secret, so store it in your server's secret manager now. Bekzod copies both, and ticks "I have stored the secret safely". The window closes. The list shows the new client with its id and the date it was created. The secret is nowhere on the page, and it never will be again. ecom keeps the client's id, but never the secret. So nobody at the bank, and nobody who breaks into ecom's database, can read it back. Now the website's server sends its id and secret to the login server. It gets back a short-lived token: a pass that expires soon. Only that token reaches the payments service. And only a machine login with the merchant's role can reach it at all. People's logins cannot, not even Malika's. On Thursday, Bekzod pastes the secret into a group chat by mistake. He does not panic. He clicks Rotate secret. The portal asks first: the current secret stops working immediately, so update your servers right after. He confirms. A new secret appears, once, with the same warning. That is rotation: a new secret is issued, and the old one stops working at once. Anyone who tries the old secret from the chat is refused by the login server. Malika's own login is never touched, and she only hears about it at lunch. A separate key for each server keeps the owner's login private. It lets the merchant cut off one leaked key in one click, without locking anyone out. And because ecom never keeps the secret, the bank cannot leak it either. Next: the people on Malika's team.
