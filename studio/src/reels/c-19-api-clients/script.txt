What should a merchant's server log in with? In lesson eighteen, two admins switched the merchant on. In lesson one, the shop's server asked ecom to create each payment. This lesson gives that server its own login, separate from any person's. Picture a merchant's developer who is told to put the owner's portal password into the server's settings. The password ends up in a shared code store. When the developer leaves, the owner's own login has to change. And every request the server ever made looks like the owner clicking buttons. You never give a cleaner your own house keys. You give them a key of their own, which you can change without changing yours. A merchant's server gets the same. Here is how it works. An active merchant creates an API client: a login for a machine, not for a person. It has an id, like a username, and a client secret, like a password that only the machine knows. The secret is shown exactly once, when the client is made. ecom keeps the client's id, but never the secret. So nobody at the bank, and nobody who breaks into ecom's database, can read it back. The merchant's server sends its id and secret to the login server. It gets back a short-lived token: a pass that expires soon. Only that token reaches the payments service. And only a machine login with the merchant's role can reach it at all. People's logins cannot. When a secret may have leaked, or the developer who knew it leaves, the merchant rotates it. That is rotation: a new secret is issued, and the old one stops working at once. The owner's own login is never touched. Only an active merchant can create or rotate an API client. Now watch the product. First, a merchant that is not yet switched on opens API clients. There is no button at all. The page says "API clients open when you are live", and explains that two bank admins must activate the account first. Now the same page for an active merchant. The page explains that the merchant's servers use these to get access tokens. The viewer clicks New client. A window opens: "Your new API client". It shows the client id and the client secret. Above them is a warning: this is the only time you will see this secret, so store it in your server's secret manager now. The viewer copies both, and ticks "I have stored the secret safely". The window closes, and the list shows the new client with its id and the date it was created. The secret is nowhere on the page, and it never will be again. The viewer's server now uses the id and secret to get a token, and the token works. Then the viewer clicks Rotate secret. The portal asks first: the current secret stops working immediately, so update your servers right after. The viewer confirms. A new secret appears, once, with the same warning. The server tries the old secret again, and the login server refuses it. What does this protect? A person's password in a server's settings leaks, and its requests cannot be told apart from the person. A separate key for each server keeps the owner's login private. It lets the merchant cut off one leaked key in one click, without locking anyone out. And because ecom never keeps the secret, the bank cannot leak it either. So, like the cleaner's own key: changed in one click, and the owner's key never touched. Next: the people on the merchant's team.
