What should a merchant's server log in with? Picture a merchant's developer who is told: use your portal password in the server's settings. The password ends up in a git repository. When the developer leaves, the owner's login has to change. And every request the server made looks like the owner clicking buttons. You would never give a cleaner your own house keys. You give them a key of their own, which you can change without changing yours. A merchant's server gets the same: an API client, a login for a machine, with the merchant role. Only an active merchant can create one. Its client secret is the password of that login, and it is shown exactly once. ecom keeps the client's id, and never the secret. The server trades its id and secret for a token. And only the merchant role reaches the payments API. When a secret may have leaked, the merchant rotates it. Rotation gives a new secret, and the old one stops working at once. Now look at what ecom keeps. The table of API clients has the client's id and the login server's id, and no column for a secret. The portal says it plainly: this is the only time you will see this secret. And before a rotation, it warns that the current secret stops working immediately. Now check it on your laptop. With the client's id and secret, the server asks the login server for a token, and gets a bearer token back. Rotate the secret in the portal, and ask again with the old one. The login server refuses: invalid client credentials. Like the cleaner's key: changed in one click, and the owner's login never touched. Next: the people who use the merchant's portal.
