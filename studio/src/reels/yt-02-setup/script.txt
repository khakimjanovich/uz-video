Where does a payment system start, if not with payments? With a stack, a build, and an environment that runs with one command. We chose Java twenty-five and Spring Boot four: long-term support, and the most widely used stack for Java services. We chose Gradle, with builds in Groovy, because the build is the pipeline: it generates code from the contracts, checks the style, runs the tests, and publishes, the same way on every machine. The app is one modular monolith with six modules, partner, commission, e POS, BIN, card, and payment: one deploy today, and clean seams for tomorrow. Each module owns its own schema in one database, and connects as its own user, which can see that schema and nothing else. A module asks another only through that module's contract, the internal operations in its OpenAPI file, and the build fails if it reaches any further. Inside, every module uses the one layout every Spring developer knows: layered, with a controller, a service, a repository, and an entity. We chose contract first: an OpenAPI file comes before any code, Gradle generates the interfaces and models, and the code must implement them, so it never drifts from what clients were promised. The same contract generates a client interface too: one module calls another through it inside the app today, and over HTTP the day that module becomes its own service. Shared pieces, the error format, security, persistence, crypto, and every contract, live in the platform folder, each with its own build. Gradle publishes each one to a Maven repository, and the app imports it by version, like any other library; the day the platform moves to its own repository, nothing else changes. A version catalog, published the same way, pins every version, so every build uses the same ones. Errors follow one format: each module lists its errors once, and the client gets a problem detail with a stable code, in English, Russian or Uzbek. Services that do one job live outside the app, each with its own contract and client: the card scheme adapters. One infrastructure repository starts all of it with Docker Compose, and each piece is explained in the episode that first uses it. One command, and the whole world is up; the code, the infrastructure, the load tests, and the web app each live in their own repository. Next, the domain, which comes before a single table.
