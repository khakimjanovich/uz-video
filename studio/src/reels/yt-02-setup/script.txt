Where does a payment system start, if not with payments? It starts with a project that builds, and an environment that runs with one command. We use Java twenty-five and Spring Boot four, with Gradle builds written in Groovy, the way the bank writes its own. The app has six modules, partner, commission, terminal, BIN, card, and payment, and each one owns its own schema, with a database user that can see nothing else. A module talks to another only through the public interface in its root package, and the build fails if it reaches any further. Shared pieces live in a platform folder, each its own build, published to the local Maven repository. The version catalog pins every version, so the build is the same on every machine. Errors follow one format: each module lists its errors in an enum, and a YAML file gives each one its HTTP status and its message in English, Russian and Uzbek. API contracts are OpenAPI files, and the code generated from them lives only in the published jars, never in our source. Every module follows the same layers, controller, service, repository, and entity, with its constants in one place. Services that do one job live outside the app, each with its own contract and client: the card scheme adapters, and the file service. A separate infrastructure repository uses Docker Compose to start Postgres and Redis, and every other tool joins only when a problem needs it. With one setting, the app logs structured JSON in the community ECS format, and reports its health from the very first minute. One command in the infrastructure repository, and the whole world is up. The code, the infrastructure, the load tests, and the web app each live in their own repository. Next, we design the domain before we write a single table.
