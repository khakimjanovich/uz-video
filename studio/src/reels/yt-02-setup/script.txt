Where does a payment system start, if not with payments? It starts with a project that builds, and an environment that runs with one command. We use Java twenty-five and Spring Boot four, built by one Gradle build with a module for each part of the domain. The app has five modules, partner, commission, terminal, card, and payment, and each one owns its own schema, with a database user that can see nothing else. A boundary test fails the build if one module reaches into another module's code or tables. Shared pieces live in a platform folder, built once and published to the local Maven repository. The version catalog pins every version, so the build is the same on every machine. The error starter gives every module the same error format: a problem detail with a stable code. API contracts are OpenAPI files, and the code generated from them lives only in the published jars, never in our source. Every module follows the same layers, controller, service, repository, and entity, with its constants in one place. A separate infrastructure repository uses Docker Compose to start Postgres, Redis, and Keycloak, and nothing else yet. Every other tool joins only when a problem needs it. With one setting, the app logs structured JSON in the community ECS format, and reports its health from the very first minute. One command in the infrastructure repository, and the whole world is up. Unit tests run in seconds, integration tests run against a real Postgres, and load tests live in their own k6 repository. Next, we design the domain before we write a single table.
