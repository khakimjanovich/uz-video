How does the bank know a request really came from the merchant, exactly as the merchant wrote it? In lesson nineteen, the merchant's server traded its secret for a short-lived token. With that token, it asks ecom to create a payment, as in lesson one. This lesson proves that each request was really written by that server, and never changed on the way. Picture a shop's server asking the bank to create a payment. The request already carries a token, the pass the merchant's API client received from the bank. But a token only says who you are. It does not say that you wrote this particular request. And tokens leak. One ends up in a log file, and anyone who reads that log can now ask for payments of any amount, with the buyer sent back to any address. There is a second danger. Someone who records one honest request can simply send it again tomorrow. So a pass alone is not enough. Think of an old letter closed with a wax seal. The seal comes from your own ring, so nobody else can make it. A broken seal shows the letter was opened. A date shows when it was written. And a serial number lets the reader notice the same letter arriving twice. The merchant's server does the same with every request. It adds a request signature: a seal over every part that matters. The seal covers the method, which says create. It covers the full address the request goes to. It covers the token. It covers a fingerprint of the body, so the amount and the return address are sealed too. And it covers the time and a one-time number. The seal is made with a signing key. That is a secret held by only two parties: the bank and this one API client. The bank writes it straight into its key safe. The payments app can read it, but never change it. When a request arrives, ecom checks it in a fixed order. First, the time must be fresh, inside the bank's chosen window. Second, the body must match its fingerprint. Third, the API client named in the seal must be the one that owns the token. Last, ecom makes the seal again with the same key and compares the two. Only then does it spend the one-time number. That number is the nonce, and each nonce works once. A nonce is spent only after the seal checks out, so a forger cannot burn a merchant's numbers in advance. One more rule follows. Only the merchant's own switched-on website, with one of its own return addresses, can take a payment. Now watch it from the merchant's server. It builds the body: the website, the order, the amount in cents and the return address. It seals the request and sends it. The answer comes back at once. The payment is created, and the answer carries the link to the bank's payment page. In the merchant portal, the payments list shows one new payment, waiting for the buyer. Now the server sends the very same sealed request a second time, unchanged. The bank refuses it. The answer says the one-time number is already used. Next, someone copies a request, changes the amount, and keeps the old seal. The bank refuses it, because the body no longer matches. Last, someone sends a request sealed long ago. The bank refuses that too, because it is no longer fresh. After every refusal, the payments list stays exactly the same. Nothing new is created. What does this protect? Without the seal, a leaked token is a blank cheque. Anyone could create payments in the merchant's name, for amounts the merchant never chose, and send the buyer back to a page the attacker controls. Without the nonce, one recorded request becomes a copy machine. The seal protects the merchant's name and every number in the request. The date and the nonce protect against copies. And the key safe protects the key itself, because no person ever types it into the app. So back to the letter. The seal says it is yours and unopened. The date says it is fresh. The serial number says it is the only one. Nobody can forge it, and nobody can post it twice. Next: what happens when the merchant's server asks for the same payment twice on purpose.
