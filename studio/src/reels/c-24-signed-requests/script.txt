Tuesday, eleven at night. Bekzod is connecting Malika's flower shop to the bank, and one test payment keeps failing. To see why, he prints the whole request into a log file, token and all. In lesson nineteen, his server traded the shop's secret for a short-lived token, and with that token it asks ecom to create payments. This lesson is about why that token alone should never be enough. A token says who you are. It does not say that you wrote this particular request. And tokens leak, exactly like this one. Bekzod's log ends up in a support chat, and anyone who reads it now holds a working token. With it, they can ask for a payment of any amount, and send the buyer back to any address they like. There is a second danger. Someone who records one honest request can simply send it again tomorrow. Most teams stop at the token. I think that is the most common mistake in payment APIs, and the cheapest one to avoid. So Bekzod's server seals every request. That seal is the request signature. It covers the method, which says create. It covers the full address the request goes to. It covers the token. It covers a fingerprint of the body, so the amount and the return address are sealed too. And it covers the time and a one-time number. Change any of them, and the seal no longer fits. The seal is made with a signing key. That key is a secret held by only two parties: the bank and this one API client. The bank writes it straight into its key safe. The payments app can read it, but never change it, and no person ever types it into the app. When a request arrives, ecom checks it in a fixed order. First, the time must be fresh, inside the bank's chosen window. Second, the body must match its fingerprint. Third, the API client named in the seal must be the one that owns the token. Last, ecom makes the seal again with the same key and compares the two. Only then does it spend the one-time number. That number is the nonce, and each nonce works once. Because it is spent only after the seal checks out, a forger cannot burn Malika's numbers in advance. One more rule follows. A payment can be taken only for Malika's own website, switched on, with one of its own return addresses. Wednesday morning, Bekzod tries it properly. His server builds the body: the website, the order, the amount in cents and the return address. It seals the request and sends it. The answer comes back at once. The payment is created, and the answer carries the link to the bank's payment page. In the merchant portal, Malika's payments list shows one new payment, waiting for the buyer. Then Bekzod plays the attacker. He sends the very same sealed request a second time, unchanged. The bank refuses it, because the one-time number is already used. He copies a request, changes the amount, and keeps the old seal. The bank refuses it, because the body no longer matches. He sends a request sealed yesterday. The bank refuses that too, because it is no longer fresh. After every refusal, the payments list stays exactly the same. Nothing new is created. So the token in that support chat is worth nothing on its own. Without the seal, it would be a blank cheque in Malika's name. Without the nonce, one recorded request could be sent a thousand times. The seal protects her name and every number in the request. The time and the nonce protect against copies. And the key safe protects the key itself.
