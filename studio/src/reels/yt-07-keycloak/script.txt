Who is calling the API, and how does the bank know? A name typed into a request header proves nothing, because anyone can type a header. So Keycloak holds every login: the bank's admins, the merchants, and the merchants' servers. The realm defines three roles: admin for bank staff, partner for a merchant's people, and merchant for a merchant's servers. Signing up takes a password, which goes straight to Keycloak and never into our database. The new login can do nothing until the email is verified, and then it gets the partner role. Every request carries a token, and the app checks it before any business code runs. The route rules live in configuration: each path needs its role, and anything not listed is refused. The admin's name comes from the token, so the history shows who really acted. An active merchant creates API clients for its servers; each one gets the merchant role, and its secret is shown only once. Rotating issues a new secret, and the old one stops working at once; our database keeps the client ids, never a secret. Next, the websites that will actually take the payments.
