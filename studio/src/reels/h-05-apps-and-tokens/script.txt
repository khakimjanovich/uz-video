On Thursday, a developer on the marketplace team turns on a debug log, and forgets it. For two days, the log writes the full marketplace tokens of its customers, and Aziz is one of them. Someone with access to the logs copies his token, and sends it to the backend of the mobile bank, to move money. The token is real, Keycloak signed it, and it has not expired. So why does the mobile bank refuse it? In lesson four, one installation sat inside the perimeter of the bank, with one Keycloak for all apps. This lesson shows how one Keycloak keeps the apps apart. Start with the realm. A realm is one space in Keycloak, with its own users, keys and settings. heeyID has one realm for the installation, so one bank has one realm. Inside the realm, each app of the bank is one client: the mobile bank, the marketplace app, the marketplace web profile and the credit service. When Keycloak issues a token, it writes two names into it. The first is the audience, aud: who the token is for. The second is the authorised party, azp: which app asked for it. In heeyID, both name the same app. So the token of Aziz says, in a signed field: marketplace, and only marketplace. Now the rule. The backend of each app accepts only the tokens of its own app. The mobile bank backend reads the audience and the authorised party, sees the marketplace, and refuses. The answer is a fixed error: session of a different app, log in again. The stolen token opens nothing but the marketplace. heeyID checks the same rule at its own door. Its request guard looks at the token before any module sees the request. It checks that the token is for this app, by the audience and the authorised party. Then it checks the device binding: the token belongs to one device record. Why not something simpler, like a header that says the app is the mobile bank? Because anyone can write a header. I think this is the main idea of the lesson: a header says what a caller wants to be, and a signed token says what it is. heeyID takes the app from the verified token, never from a header or a path. There is one moment with no token: the start of a registration, or of a login. Then the app comes from the app identifier of the build, and heeyID checks it against its catalogue of apps. The same rule goes deeper than the door. Each session and each app account carries its app. Each query of app data filters by the app of the token, and the repository layer adds that filter, not the caller. So even a bug in a module cannot read the marketplace account through a mobile bank session. Cache keys with app data carry the app, and each event carries the app. When one app needs data of another app account, it asks through a request that the customer answers, for example the address-sharing request in the master app. Back to the leak. What does the person with the logs get? The marketplace, for Aziz, for a short time. The access token lives only for a short, configured time. The refresh token rotates at each renewal, and the platform detects a refresh token that comes back a second time. And the session is bound to the device of Aziz. That is a real incident for the marketplace team, but it is not a way to the money of Aziz. How do we know it stays this way? At each release, the acceptance tests send a marketplace token to the mobile bank backend, and expect that error. If a release forgets the check, the release stops. One more thing comes with one realm. A new app of the bank is one more client and one more row in the app catalogue, not a new installation. Each app gets its own required level. The credit service can need level two, while another app needs only level one. To recap: one realm for the installation, and one client for each app. Each token names its app two times, as the audience and the authorised party. Each backend accepts only its own tokens, and heeyID checks the same at its door and in every query. So the leaked token stays in the marketplace. But look at the values in this lesson: the token lifetime, the required level of each app, the limits. Who sets those values, and where do they live? Next: configuration.
