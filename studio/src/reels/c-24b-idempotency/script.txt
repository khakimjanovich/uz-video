What happens when a merchant's server asks for the same payment twice? The server sends create payment, the network hiccups, and no answer comes back. So it sends the same request again. Without a way to tie the two together, the buyer gets two payment pages, and may pay twice. Think of a lift button. Press it once or ten times, and one lift comes. So each create carries an idempotency key: the merchant's own name for this attempt. The same key with the same body gets the first answer back, unchanged. That is an idempotent replay, and the answer says so in a header. The same key with a different body is refused, because it is a different request under an old name. And two retries can arrive at the very same moment. They meet at the database's unique key: one wins, and the other gets the winner's answer. Now read it in the code. Each idempotency record keeps the merchant's client, the key, a fingerprint of the request, and the first answer. The client and the key together are the primary key, so the same pair can never be stored twice. Before creating anything, the service looks for an earlier record with that key. A different fingerprint is refused, and the same one returns the stored answer, marked as a replay. And if a racing request wins the insert, the service simply runs again, and replays the winner's answer. Like a lift button: press as often as you like, and one payment comes.
