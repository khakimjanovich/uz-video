What happens when a merchant's server asks for the same payment twice? Picture the shop's server at checkout. It sends the bank a request: create a payment for this order. Then the network hiccups. The request may have arrived, or it may not. The answer never comes back. The server cannot tell which half was lost. So it does the sensible thing and sends the request again. Without care, the bank now creates a second payment. The buyer may get two payment pages for one order. A nervous buyer may pay both. Then the shop has to give money back, and the buyer has lost trust. Retrying is right. The problem is a retry that the bank cannot recognise. Think of a lift button. You press it once, and a lift is called. You press it ten more times, because you are in a hurry. Still one lift comes. Each press means the same thing: I want a lift here. A payment request should work the same way. So each create carries an idempotency key. That is a plain name the merchant gives to this one attempt, such as the order and a counter. The merchant chooses it, and it stays the same on every retry of that attempt. The bank remembers each key for each API client, together with the request it came with and the answer it gave. Now three things can happen. First, the same key arrives with the same request. The bank does not create anything. It sends back the first answer again, with the same payment and the same page link. It marks that answer as an idempotent replay, so the merchant's server can see it is a repeat. Second, the same key arrives with a different request, for example a different amount. The bank refuses it. That is a different request under an old name, and guessing which one the merchant meant is never safe. Third, two retries arrive at the very same moment. Both look new, because neither has been saved yet. They meet at one place in the bank's records, where each key can be written only once. One wins and creates the payment. The other loses, and gets the winner's answer back. There is one detail from the previous lesson. Every retry still needs a fresh seal, with a new time and a new one-time number. So the server seals the request again, but keeps the same idempotency key. The seal stops copies made by strangers. The key ties together the retries made by the merchant. Now watch it from the merchant's server. It sends create payment with its key. The answer is lost on the way. It seals the same request again and sends it with the same key. This time the answer arrives. It holds the same payment and the same page link as the first, and it is marked as a replay. In the merchant portal, the payments list shows one payment for this order, not two. Now the server reuses the key, but with a different amount. The answer is a refusal that says the key was already used for another request. The list still shows one payment. What does this protect? It protects the buyer from paying twice for one order. It protects the merchant from refunds and angry calls caused by a bad network. And it lets the merchant's developers write the simplest safe rule there is: when in doubt, send it again with the same key. Without the key, every timeout forces a hard choice between a lost order and a double charge. With it, retrying is always safe. So back to the lift button. Press it once, or press it ten times. One lift comes, and one payment is made. Next: the page the buyer opens.
