The eighth of March is the busiest day of Malika's year. At ten past six in the evening, a buyer presses pay for order 1042. Bekzod's server asks the bank to create a payment, and the mobile network hiccups. The request may have arrived, or it may not. The answer never comes back, and the server cannot tell which half was lost. In lesson twenty-four, every request carried a seal, and a copied request was refused. This lesson makes an honest second request safe: however many times it is sent, one payment comes. So the server does the sensible thing, and sends the request again. Without care, the bank now creates a second payment. The buyer may get two payment pages for one bouquet. A nervous buyer, on the busiest evening of the year, may pay both. Then Malika has to give money back, and she has lost a customer's trust. Retrying is right. The problem is a retry that the bank cannot recognise. So every create carries an idempotency key. It is a plain name Bekzod gives to this one attempt, such as the order number and a counter. The merchant chooses it, and it stays the same on every retry of that attempt. The bank remembers each key for each API client, with the request it came with and the answer it gave. Now three things can happen. First, the same key arrives with the same request. The bank creates nothing. It sends back the first answer again, with the same payment and the same page link. It marks that answer as an idempotent replay, so Bekzod's server can see it is a repeat. Second, the same key arrives with a different request, say a different amount. The bank refuses it. That is a different request under an old name, and guessing which one the merchant meant is never safe. Third, two retries arrive at the very same moment. Both look new, because neither has been saved yet. They meet at one place in the bank's records, where each key can be written only once. One wins and creates the payment. The other loses, and gets the winner's answer back. One detail ties this to the last lesson. Every retry still needs a fresh seal, with a new time and a new one-time number. So the server seals the request again, but keeps the same idempotency key. The seal stops copies made by strangers. The key ties together the retries made by the merchant. People mix these two up all the time, and they are opposites: one refuses repeats, the other welcomes them. Here is order 1042 again. The server sends create payment with its key. The answer is lost on the way. It seals the same request again and sends it with the same key. This time the answer arrives. It holds the same payment and the same page link as the first, and it is marked as a replay. In the merchant portal, Malika's payments list shows one payment for this order, not two. Then Bekzod tests the edge. He reuses the key with a different amount. The answer is a refusal that says the key was already used for another request. The list still shows one payment. I think this is the simplest rule a developer can be given, and the most valuable one. When in doubt, send it again with the same key. Without the key, every timeout forces a hard choice between a lost order and a double charge. With it, the buyer pays once, Malika gives nothing back, and nobody calls her angry on the eighth of March. Next: the page the buyer opens.
